## 0. 总判

**A 组可封口；B/C 建议案大部可收，但仍有两个 P0 阻断项。**

阻断项：

1. **B2 的 merge-as-obligation 尚未产生全局串行性。**CLAIM 只互斥同一 obligation 的
   winner；不同 PR 的两个 merge obligations 可以同时 active。per-seat ref 又只在同 seat
   内竞争，跨 seat 更不会互斥。必须补“唯一 merge coordinator + capacity=1 的 merge slot”
   或改用真正共享的全局 CAS。
2. **C5 的“未知 type/version 跳过继续”不安全。**旧内核若跳过未来的 CANCEL、授权收紧或
   新 blocking event，可能在事实不完整时 merge。未知语义不应 quarantine 为损坏，但必须

3. B1 的 gate CLAIM 应记录 `revision_at_claim={base,head}`，不能只写 `head_at_claim`；

## 2. B 组 B1–B5

### B1 obligation id 合流案 — 有条件同意

稳定 id 比把 head 放进 id 更好：

```text
obligation_id = hash(assignment_revision, kind, target_key, aspect)
```

它保留同一义务的 claim/reclaim/handoff/cancel 历史句柄；head 前进只创建新 attempt，不制造
新逻辑义务。我的两项原诉求仍成立：

- assignment revision 变化 ⇒ obligation id 变化，旧 claim 不能跨 policy revision；
- verdict exact revision + active claim 引用 ⇒ 旧 verdict 不会满足新 revision。

但建议案只写 `head_at_claim`，与 B2 strict base 不闭合。应改为：

```json
{
  "obligation": "<stable-id>",
  "revision_at_claim": {
    "base": "<full-oid>",
    "head": "<full-oid>"
  }
}
```

对 gate：

```text
current {base,head} != revision_at_claim
    => claim stale
    => obligation eligible for explicit re-claim
```

“回池”只表示 attention state，不表示内核自动 re-claim。author claim 不随 head 前进 stale，
仍跟 assignment+slug 生命周期。

还需钉死四个字段级细节：

1. `target_key` 对 gate 至少含 change/PR identity 与 gater seat；`aspect` 为 gate id。否则两个
   gate leaves 可能误成同一 obligation。
2. assignment static source 在线上保留 `{commit,path,blob}`；id preimage 至少使用 blob OID
   与 assignment logical id。loader 拒绝项目内重复 logical id。
3. hash 要有版本与 domain separation，例如：
   `sha256("hctl-obligation-v1\0" + canonical_json(key))`。
4. event 同时保存结构化 preimage 与 derived id；只存一串 hash 会让审计与 schema 错误诊断
   变差。

head 从 H1 变 H2 又回 H1 不是安全漏洞：若 base/head 全同，它就是同一内容 revision；
若 base 不同则 exact tuple 仍 stale。remote branch 回卷本身另由 ref integrity 规则报警。

### B2 base freshness + merge 串行化 — strict base 同意，串行化当前不成立

strict `{base,head}` 作为 P1 规则可接受：先吞吐换确定性，真实 round 后再讨论 tracking base。

问题在“merge obligation 走 CLAIM，所以串行化白送”。反例：

```text
MA = PR-A 的 merge obligation
MB = PR-B 的 merge obligation

claim(MA) 成功
claim(MB) 也可成功
```

即使 MA、MB 都由同一 seat 记录，per-seat ref 只保证两次 append 有顺序；若 derive 没有
capacity predicate，两个不同 obligation 仍可同时 active。若分配给不同 seat，它们写不同
refs，甚至不会发生 CAS 竞争。

建议采 27d 所称 coordinator 案，但把缺失条件写全：

1. project 配置唯一 `merge_coordinator=<seat>`；
2. 所有 merge obligations 只能分配给该 seat；
3. coordinator 有 repository-wide `merge_capacity=1`；
4. claim writer 在同一 coordinator ref snapshot 上检查“当前无 active merge claim”；
5. 同窗口两化身基于同 tip 竞争时，ref CAS 只让一方发布；败者 fetch 后因 capacity 已满被拒；
6. merge receipt / CANCEL / overdue re-claim 才关闭或取代 active merge claim。

这才是“merge-as-obligation + coordinator slot”，而不是普通 CLAIM 自带的性质。若不愿引入
capacity predicate，就只能使用一条真正共享的 global merge ref；前者更贴合现有 slot 模型。

完整流程：

```text
claim merge slot
→ fetch main / PR head / relevant event refs
→ exact {base,head} + quorum re-check
→ gh pr merge --squash --match-head-commit <head> --body-file <receipt>
→ fetch main
→ 验 squash commit parent == base
→ 验 receipt
→ receipt 关闭 merge claim
```

`--match-head-commit` 只保护 head，不保护 base。coordinator slot 只串行 cooperative hctl
merge；网页 merge/直接 push 仍是既定信任边界。post-merge 若发现 parent≠receipt base，
只能报完整性事故，无法假装事前拒绝。

merge receipt 字段不要留 `...`，P0 应封成：

```text
Hctl-Version: 1
Hctl-Assignment: <assignment-revision-oid>
Hctl-Obligation: <merge-obligation-id>
Hctl-PR: <number>
Hctl-Base: <full-oid>
Hctl-Head: <full-oid>
Hctl-Merge-Claim: <claim-event-oid>
Hctl-Method: squash
Hctl-Fact-Tip: <seat>=<event-tip-oid>   # 可重复
```

重复的 `Hctl-Fact-Tip` 钉住 quorum evaluator 实际读取的各席链 prefix；否则未来链继续追加后，
很难无时钟地重放“merge 当时看到的事实集合”。derive 还要验证 main commit 的单 parent
就是 `Hctl-Base`。

### B3 EDGE→ASSIGN + memo namespace — 同意

全接：

- `assignment.schema.json` / `.hctl/assignments/` / `ASSIGN`；
- `work/<seat>/<slug>` 只承载 author-class；
- `memo/<seat>/<slug>` 只承载 memo lane；
- seats 分列 author/memo patterns；
- doctor 做跨 seat、跨 lane 不相交验证；
- 历史 `work/<seat>/memo-*` 不重写。

这是 naming 修正，也是把 memo 不占 slot 从纪律升到结构。

### B4 派工/取消授权面 — policy 可用，执行等级需降

三行授权表符合当前“人=排班/开工/裁决”的产品模型，但：

```json
{"authorized_by": "user"}
```

是转录席写下的 assertion，不是 Git/GitHub 可验证 principal。任一能写 event ref 的 seat 都能
填这串字。因此要拆开两条不变量：

- “ASSIGN/CANCEL 确由人发起”：当前信任前提/级④，靠 prompt 与审计；
- “begin/verdict/merge 必须有冻结 assignment”：hctl 可级②拒绝。

不要把第二条的机械性倒灌成第一条已经被机器证明。若未来进入多真人/对抗 profile，才需要
签名 control ref、独立账号或 capability token；bootstrap 不应现在造。

schema 建议：

- event `actor` 记录转录 seat/machine/session；
- `authority: {kind:"user"}` 记录声明，不叫 proof；
- CANCEL 精确引用 assignment revision / obligation / claim；
- 同 logical assignment id 出现冲突 payload 时 `AMBIGUOUS_ASSIGNMENT`、写动作 fail closed；
- 重复的同内容 CANCEL 可幂等折叠；
- escalate 不得隐式创建 ASSIGN。

### B5 fencing：claim OID — 同意

claim event OID 就是充分 fencing token，无需 epoch：

- re-claim 精确 `reclaim_of=<active-claim-oid>`；
- VERDICT、HANDOFF、merge receipt 等完成/转移事实引用 active claim OID；
- derive 拒绝 stale claim 产物；
- “第几代”从同 obligation 的 accepted CLAIM 拓扑数派生。

epoch 与 claim OID 提供同一比较，OID 少一个计数器及其漂移路径。

## 3. C 组 C1–C9

### C1 pending commit 替代 event UUID — 有条件同意

P1 可以不设 `event_id` UUID。只要 local publishing ref 是 durable pending journal，commit
OID 已是 operation identity。

27d 的“看 remote tip 是否即 pending commit”覆盖不全。逐一对照中间态：

| 状态 | 正确恢复 |
|---|---|
| local CAS=C，尚未 push，remote=R | publishing≠tracking；重推原 commit C |
| push 成功但 response 丢失，remote tip=C | C==tip，确认 delivered |
| push 成功后别的 writer 又 append D | `C` 是 `D` ancestor，仍确认 delivered，再把本地对齐 D |
| push 被竞争者 D 抢先，C/D 从 R 分叉 | C 不是 D ancestor；确认 lost，存 recovery 后 CAS 对齐 D |
| remote ref 回卷/删除 | fetch/ls-remote 报 integrity error，不猜历史是否曾接受 C |
| 同机第二 writer 看见 publishing≠tracking | 拒绝新 append，只允许恢复 pending |

因此判据应是：

```text
git merge-base --is-ancestor <pending-commit> <remote-tip>
```

而不是只比较 tip equality。**blob OID 不应作 event identity 兜底**：两个合法事件可以有完全
相同 JSON blob，但 parent/claim generation 不同；commit OID 才编码 parent、tree 与提交元数据。

一笔事务已完全 settle 后，调用方重发同一语义命令可能多一条等价 VERDICT/NOTE；这应由
state-aware command（已有 active claim / 当前 revision 已有相同 latest verdict）返回现状，
而不是靠一个 hctl 内部生成、调用方未持久化的 UUID。若未来有外部 RPC caller，再增加 caller
提供的 idempotency key，不必塞进 P1 每个 event。

### C2 publishing/tracking refs — 同意

`refs/coop/<seat>` 保留权威 publishing namespace，
`refs/hctl/remotes/<remote>/coop/<seat>` 作本地 observation，方向正确。

tracking fetch 不带 force 可把 remote rollback 变为响亮 non-ff；remote deletion 另由
`ls-remote` 集合比较发现。协议必须保证 tracking ref 只由 fetch 更新，不能在 push response
到来前乐观前移。

### C3 三 schema — 有条件同意

接受 27d 列出的 codex 骨架与有限 quorum AST；合入以下修正：

1. gate CLAIM 使用 B1 的 `revision_at_claim={base,head}`；
2. merge coordinator/capacity 与 receipt 字段进入 assignment/METHOD；
3. unsupported type/version 按 C5 新规则；
4. `actor.session` 可显式 null，不参与 correctness；
5. `max_severity` 若保留，只作 display/audit，P1 可直接省略。

字段命名还需一次收束：27c 同时出现 `v`/`timestamp`，corpus 使用 `v`/`ts`，codex envelope
使用 `schema_version`/`created_at`。不要三套并存。建议采用自描述的：

```text
schema_version: integer
created_at: RFC3339 UTC string
```

链已经提供排序，照抄 appraise 的“10 位零填充 epoch string”只是在复制 notes 为字符串排序而
造的 workaround。created_at 与 commit timestamp 都只作审计，不参与 winner 或 correctness。

### C4 threshold 语义 — 有条件同意

同意 `decision` 是唯一 merge 语义，内核不从 severity 猜 verdict。相应地应诚实改写 K-05：

- threshold 是给 gater 的**决策输入/审题参数**；
- 它不是 evaluator 自动运算的 blocking axis；
- gater 在 assignment revision 指定的 threshold 下只选
  APPROVE / REQUEST_CHANGES；
- event 绑定该 gate obligation/assignment revision，证明它回答的是哪份 policy；
- `max_severity` 如保留只展示，不覆盖 decision。

若仍把 threshold 称“内核四轴之一”，读者会期待 hctl 根据 severity 自动放行，和 C4 相矛盾。

### C5 结构坏 / 语义未知两分法 — 反对，改三分法

“新 type/新版本跳过继续”可用于 append-only 评论集合，不适合含 CANCEL/授权/gate 的控制日志。
旧 binary 跳过一个未来 blocking event 后 merge，是 silent skip 的另一种写法。

建议：

1. **结构损坏**：非线性、多 parent、非法 JSON、seat/ref 不符
   → `CORRUPT_CHAIN`，整链 quarantine，相关写动作 fail closed。
2. **结构合法但语义不支持**：未知 type、未知 major/schema version
   → `UNSUPPORTED_FACTS`，保留对象、展示已知 prefix 与未知 event OID；相关写动作 fail closed，
   提示升级 hctl。
3. **当前版本明确定义为非语义的已知 event**：例如 NOTE
   → schema 校验后可忽略其 message，不影响 gate/slot。

前向兼容的正确含义是新 reader 能读旧事实；不是旧 writer 可以假定未来控制事实无效。

### C6 执行等级表 — 同意

hooks=级③、remote append-only=级③检测+备份、级④只留 memo 质量/知识上迁，均比原表诚实。
本地 writer 的 one-parent CAS 仍可标级②；不要把它扩写成 server 永不可回卷的级①。

### C7 失败行为章 — 有条件同意

`INCOMPLETE_FACTS`、rollback recovery ref、可选第二 remote、`UNRECORDED_MERGE` 都同意。

“补记不猜”还缺 wire form。P1 可先规定：

- 没有结构化 receipt 的 main commit 永不自动转成 recorded；
- operator 未提供 exact assignment/base/head/PR/claim 前始终红灯；
- 修复事实必须 forward-only，明确引用被补记的 main commit；
- 在 repair event/attestation schema 尚未定前，允许债保持 unresolved，不要借 NOTE 偷渡
  correctness。

若后续要闭合，可增加显式 `hctl repair merge-receipt` 产生可审计 attestation；它是否进 event
闭集由 P2 再裁。

### C8 命令面 — 同意

- 增 `hctl claim`；
- `begin` formal 默认，先 claim 后建/adopt 正式 branch；
- `--draft-only` 明示本地 speculative、零远端权利；
- `run` 移 adapters；
- `wake` 改 `wait`，help 为 “block until attention set changes or timeout”。

实现上没有新冲突。formal begin 若 claim 成功后 branch 操作失败，重跑应发现同一 active
author claim 并继续，不得再铸 claim。

### C9 阻尼与 standby — 同意

不自动 re-claim、第二次以上 re-claim 红灯+escalate、standby 非对称作为推荐默认，均合适。

补精确定义：

- window = 同一 assignment revision + stable obligation，自上一次 completion/CANCEL 起；
- 只计远端链上 accepted CLAIM，不计本地/remote CAS loser；
- `reclaim_of` 链必须连续引用当前 active claim；
- “第 ≥2 次 re-claim”表示初始 claim 后至少已有两个 accepted replacements；
- status/escalate 是展示与出口，不自动 sleep、不自动造新 event。

## 4. 对 27d §5 四个 codex 定向问题的直接回答

### 1. B1 合流键是否满足 revision 锚定与旧 verdict 不复用？

**满足，条件是 gate claim 从 `head_at_claim` 升为 exact
`revision_at_claim={base,head}`，且 obligation key 的规范化/hash 规则定死。**

head 不进 stable id 没有我不能接受的歧义；它把“逻辑义务”与“某次 revision attempt”正确
分开了。

### 2. C1 pending commit 能否替代 event UUID？

**P1 能。**五类中间态都能由 publishing/tracking refs + pending commit ancestry 覆盖。
修正点是用 commit ancestry，不是 tip equality；blob OID 只作 payload审计，不作 event identity。

### 3. B2 merge-as-obligation 是否闭合 merge TOCTOU？receipt 完备吗？

**当前未闭合。**普通 obligation claim 没有跨 obligation/global capacity 语义。补
“唯一 coordinator + merge_capacity=1”后，能闭合 cooperative hctl merge 的 TOCTOU。

receipt 需使用 §2-B2 的封闭字段清单，并增加重复 `Hctl-Fact-Tip`；同时验证 squash commit
parent 与 `Hctl-Base` 一致。

### 4. C8 wait 改名与 formal begin 实现面复核

**均同意。**`wait` 比 `wake` 符合实际阻塞语义；formal begin 让弱 harness 不会把本地草稿
误报为已取得 author slot。失败重试必须复用现存 active claim。

## 5. P0 前建议新增的 corpus

1. gate head 不变、base 前进：旧 claim 与 verdict 都 stale；
2. 同 coordinator、两个不同 merge obligations：第二个 claim 被 capacity=1 拒绝；
3. merge obligation 被错误分给非 coordinator：schema/loader 拒绝；
4. ambiguous push 已成功，remote 又追加 descendant：pending commit ancestry 判 delivered；
5. pending commit 与 remote winner 分叉：判 lost 并 recovery；
6. 合法 JSON + 未知 event type/version：status=`UNSUPPORTED_FACTS`，merge 拒绝；
7. merge receipt 多 `Hctl-Fact-Tip` 重放 quorum，parent 必须等于 receipt base；
8. `authorized_by:user` 不冒充机器 proof；缺 assignment 的 begin/verdict/merge 仍拒绝；
9. formal begin：claim 成功、branch 创建失败、重跑复用原 claim；
10. 同 payload blob 出现在不同 parent：不得按 blob OID 折叠成同一 event。

## 6. 最终建议

27d 可作为终裁底稿，但用户终裁前建议主笔先把以下三句改进正文：

1. B1 `head_at_claim` → `revision_at_claim={base,head}`；
2. B2 “CLAIM 白送串行化” → “唯一 merge coordinator + capacity=1 slot，CLAIM 实现该 slot
   的跨化身竞争”；
3. C5 “未知 type/version 跳过继续” → “`UNSUPPORTED_FACTS`，读可部分展示，相关写
   fail closed”。

再把 C1 的 exact-tip 判据改为 pending commit ancestry、B4 授权来源降级为信任声明，即可
从精密堂角度进入用户终裁。
