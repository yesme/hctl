### #6 的最小修复

不必把 `commit`、`path` 放进 obligation hash；原要求本来就是“source 在线上保留，preimage
至少用 logical id + blob”。建议把 §2.1 增补为：

```text
static assignment revision MUST retain source={commit,path,blob};
obligation preimage uses assignment={id,blob}.
```

这样既保留稳定 id 的既定裁决，也能在审计时从 event 反查“哪个 main commit 的哪个路径提供
这份 blob”，避免只有内容、没有来源。

## 2. 六项新增设计

### ① HANDOFF 两形态 — REQUEST_CHANGES

**同席跨化身零事件可签收；跨席 `pending_accept` 尚未保全唯一认领。**

同席 claim 是席级资产，machine/session 只作 provenance，因此换化身不关闭 claim、不制造
协议事件，物理上正确。

跨席 happy path 也保留了显式接受：

```text
A: HANDOFF(H) -> pending_accept(B)
B: CLAIM(reclaim_of/accepts=H)
```

但超窗回池路径重新引入了跨 ref 竞态。最小反例：

1. A 在 `refs/coop/A` 发布 `H`，义务进入 `pending_accept(B)`；
2. 临近超窗，B 基于仍有效的快照，在 `refs/coop/B` 发布接受 `CB`；
3. C 基于已超窗的快照，在 `refs/coop/C` 发布回池后的认领 `CC`；
4. `CB` 与 `CC` 都引用 H，却更新不同 ref；两个 lease/CAS 均可成功。

事实并集最终含 H 的两个互斥后继。`reclaim_of` 只能校验“我看见的前件”，不能让不同 seat
ref 发生物理竞争；这正是普通 union 不提供 mutex 的同型问题。“pending 期间他席不可抢”
只覆盖 deadline 前，不裁定 accept-vs-timeout 边界。

须二选一：

- 给跨席 ownership transition 一个稳定的单 CAS 仲裁域，ACCEPT 与 TIMEOUT_RETURN 都在该域
  串行，再由各席链记录结果；或
- 维持 P1 最小面：P0 明记 cross-seat HANDOFF 状态机 **UNSUPPORTED/DEFERRED**，P2 在仲裁域
  定案后才开放，不先宣称“无双空/双赢窗口”。

建议选第二项。HANDOFF 本就在 P2 实装，不应为它扩大 P1。

### ② escalated 为推导态、三径解冻 — APPROVE

推导态消除了可通过重复 escalation event 改变 correctness state 的写放大面；advisory NOTE
不碰 gate/slot，分层正确。解冻只允许：

- 用户 CANCEL(claim)：回池并显式重置；
- 用户 CANCEL(obligation)：终结；
- 新 ASSIGN revision：产生新义务身份。

这三径都复用既有动词，且与“ASSIGN/CANCEL 的人发起是级④信任前提”一致。计数何时进入
escalated、进度与 frozen 的优先级属于新增项④，修正④不改变本项“推导态而非事件”的批准。

### ③ coordinator 绑定与 `.hctl/**` 过渡 — REQUEST_CHANGES

`merge_coordinator=claude` 作为 bootstrap 配置值可以接受；唯一席位是 capacity=1 能落在单
CAS 域上的必要结构，并不要求该 seat 永久神圣化。

但当前 rebind 与过渡规则各留一洞：

1. **rebind 只说走 gated PR，没有 slot 迁移语义。**旧 coordinator 尚有 active merge claim
   时切到新 coordinator，旧、新两条席链可能各承载一个 active slot。配置 gate 证明“谁批准
   变更”，不自动 fence 旧 slot。
2. **“P1 merge wrapper 落地前例外，随 P1 交付自动终止”不是机器可判的边界。**不同 writer
   可对“已落地”的时点有不同理解；例外又恰好覆盖能修改 seats/coordinator/policy 的路径。

P0 至少补：

```text
coordinator_config_revision is a merge-claim dependency;
rebind MUST fail while an active merge claim exists,
or MUST first CANCEL/fence that claim under the old coordinator domain.
```

过渡终点应钉一个可重放事实，例如“activation commit OID 成为 main ancestor 后启用 gate”，
而不是里程碑 prose。activation 前明确标级④ bootstrap trust；activation 后 loader/writer
级②拒绝无 required gate 的 `.hctl/**` 变更。

### ④ 红线计数取齐 — REQUEST_CHANGES

“首次 re-claim 黄；第二次 re-claim（第三个 accepted CLAIM）且无进度红”忠实调和了 Codex
所说的“第 ≥2 次 re-claim”，阈值本身批准。

尚缺的是可重放状态机：

- §3.6 一处说“进度插入 ⇒ 计数降黄/重置”，另一处又说 escalated 只能经
  CANCEL(claim)/CANCEL(obligation)/新 ASSIGN 解冻。若红后出现进度，前句像自动清红，后句
  禁止清红，优先级冲突。
- branch tip、memo merge、seat event 分属不同 ref；仅凭墙钟不能证明某个进度位于两次
  CLAIM 之间。若 re-claim 不携带它所观察的进度锚点，同一事实集合可能因读取顺序不同而给出
  不同 streak。

建议把规则写成确定函数：

```text
if escalated:
    stay frozen until one of the three explicit thaw transitions
else:
    streak = consecutive accepted replacement CLAIMs since the latest
             causally evidenced progress/reset marker
    streak == 1 -> yellow
    streak >= 2 -> red + escalated
```

“causally evidenced”须由 CLAIM 的 revision/observed fact OID 或所钉 snapshot tips 证明；
不能用采样时钟猜。进度只能在进入 escalated 前重置 streak，不能成为第四条隐式解冻径。

### ⑤ obligation preimage — REQUEST_CHANGES

语义键集大体足够：assignment revision、kind、change target、gate/gater aspect 能区分 P1 的
author/gate/merge obligation；head 不进 id 的裁决也保持。

但字节级 identity 尚未闭合：

1. `canonical_json` 没有规范引用或自定义字节算法。不同实现的 key order、Unicode 与 escape
   选择可能为同一对象算出不同 id。P0 必须钉 RFC 8785/JCS 或等价的 UTF-8 规范化算法及测试
   向量。
2. `aspect="<gate-id>:<gater-seat>"` 是二字段拼接，却未规定 token 是否禁 `:`、是否转义。
   最稳妥是保留结构：

   ```json
   {"gate_id": "<id>", "gater_seat": "<seat>"}
   ```

   若坚持字符串，schema 必须给不含分隔符的闭集 grammar。
3. 与 checklist #6 相同，event/source 还须保留静态 `{commit,path,blob}`；它不进入 hash，
   但不能从 wire form 消失。

另请把 27f 的“canonical_json 五键”改为“固定结构的 canonical preimage”；当前顶层实际是
四键（`assignment/kind/target/aspect`），称“五键”会让 schema 作者误以为另有一个顶层字段。

### ⑥ 评审收敛纪律 — REQUEST_CHANGES

方向正确：full 后只审 findings fix + delta，强制 completeness，late finding 例外化而非禁止。
但当前 wire form 与安全语义有四处冲突：

1. 27e 把 `scope.kind` 定为 `full | delta | fix_verification` 单值；27f 强制示例却填
   `fix_verification+delta`。该值不属于闭集。本 memo 为遵守本轮派工照填，但 schema 会拒绝。
2. delta 缺少 `from_blob/to_blob`，fix verification 缺少 finding IDs；只写目标 27e blob
   不能机械重建范围。
3. 27e 说 merge 前 late finding 通过同 revision 的 latest-wins verdict 处理，允许它阻断；
   27f verdict 模板却写“一律不阻塞本轮、入 backlog”。后者会让已知安全缺陷 fail open。
4. “轮次有限收敛”不是由范围函数证明的。fix 可以持续引入新 delta，delta 内也可持续产生
   新 finding；该纪律能防止无理由重开、促进收敛，但没有 well-founded measure 就不能保证
   termination。

建议 wire form 改为：

```yaml
scope:
  kind: composite
  parts:
    - kind: fix_verification
      findings: ["codex-27b#B2", "codex-27b#C5", "..."]
      target_blob: "<27e>"
    - kind: delta
      from_blob: "<27d>"
      to_blob: "<27e>"
completeness: COMPLETE
decision: APPROVE | REQUEST_CHANGES
```

required quorum 只能计入同时满足以下条件的 verdict：exact target revision、`COMPLETE`、
`APPROVE`，且 scope 覆盖 assignment 要求的 review 面。一个窄 delta 上的 COMPLETE 不能脱离
既有 full verdict 独自冒充全量批准。

late finding 则保持 27e 的安全版本：

- merge 前：标注逸出原因，发布 latest-wins verdict；若是 REQUEST_CHANGES 就阻断；
- merge 后：NOTE + 人裁修复 assignment；
- “不重启整个封口面”可以保留，但不能写成“不阻塞”。

最后把“保证有限收敛”降为“构造性促进收敛并使逸出可审计”；若真要终止保证，另设用户终裁、
round budget 或 well-founded 变更度量，不应从 scope 单调性直接推出。

## 3. P0/P1 最小收口

本轮发现不要求扩大 P1。建议边界：

| 阶段 | 必须收口 | 明确不进 |
|---|---|---|
| P0 METHOD/schema | static source `{commit,path,blob}`；canonical preimage 字节规范；coordinator activation/rebind；re-claim streak/frozen 确定函数；review composite scope 与 late-finding 语义；cross-seat HANDOFF 标 `DEFERRED` 或定义单仲裁域 | 不实现 HANDOFF、wait、repair |
| P1 单竖切 | static assignment → same-seat CLAIM → VERDICT → quorum → unique coordinator merge slot → squash receipt；未知事实 fail closed | dynamic ASSIGN、cross-seat HANDOFF、NOTE/presence、standby 自动化 |
| P2 | 在单仲裁域方案有 corpus 后开放 cross-seat HANDOFF；再做 wait/repair 等 | — |

这样修正的是 P0 的可执行规格，不把 P2 协议复杂度拖进 P1。

## 4. 建议新增的最小 corpus

1. `pending_accept` 临界点：目标席 ACCEPT 与第三席 TIMEOUT_RETURN 在不同 ref 并发，只能有
   一个 accepted transition；若当前设计做不到，P0 必须报告 unsupported。
2. coordinator rebind 时旧席有 active merge claim：配置变更拒绝或先显式 fence；新旧席不可
   同时各得 slot。
3. 第三次 accepted CLAIM 后进入 escalated，再出现 branch progress：不得自动解冻；仅三条
   显式 transition 可清。
4. 同一 preimage 的不同 JSON key order/escape/Unicode 表示必须得同一 obligation id；非法
   非 canonical input 必须拒绝或先规范化。
5. `scope.kind=composite` 的 fix+delta verdict 可校验；delta-only COMPLETE 不得满足要求
   full coverage 的 quorum。
6. merge 前 late finding 发布 REQUEST_CHANGES：latest-wins 后 quorum 立即失绿，不能只入
   backlog。

本轮复跑既有两案：

```text
PASS chain-claim-mutex
PASS notes-union-antimutex（反面展品：union 合并使双 CLAIM 并存）
```

第一案再次证明互斥来自**同一 ref 的 CAS**；它不能外推为两个 seat ref 之间也有 mutex。
