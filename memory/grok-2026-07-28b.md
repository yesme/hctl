## 1. 为什么现在谈

正式 `enforcement=active`（activation）之前，用户要先看清：

1. 这么久 dogfood，**到底暴露过什么问题**；  
2. 事后长出来的「护栏」——**有多少软件真会拦，有多少只写在文档和习惯里**。

两问绑在一起：若护栏多半是散文，通电的安全感来自别处；若关键路径已经是命令拒绝，通电主要是**关掉图方便的口子**。

## 2. 我们主要发现过什么（按层）

### 2.1 协作「物理层」出事：未过审就合进 main

- **PR #25**：required gate 未绿时被合入；协调者猜 PR 号、直接 `gh pr merge`。  
- **后果**：普通评审升级成**合入后的审计债 + 长长的 fix-forward**（#38 及后续）。  
- **拆开看**：  
  1. PR 号不是从义务/分支推出来的；  
  2. merge 没有「评审过了才能合」的硬前置（bootstrap 还开着自开自合）；  
  3. 一串命令中间没有校验点。  

**教训**：走 `hctl merge` 时，没过审就该合不了；走 GitHub 网页/`gh` 仍可绕——**保证绑在用不用工具上**。

### 2.2 测试全绿也会骗人（假绿）

反复最高密度的一类问题：`pass=N/N` ≠ 不变量成立。

| 形态 | 大意 |
|---|---|
| 双权威 | Python 侧说 OK，Go 内核拒绝 → 不能拿「脚本绿」当规范 |
| 共享沙盘代打 | 多支用例共用一个环境，**别席残留的错误**让后面的断言仍「匹配成功」 |
| 假调用 | 发现有个可执行文件就盖章，**没真正跑** hctl 也算过 |
| 负例没打到目标 | 看起来在测 A，其实更早的检查已经拦住了 |
| 测试自己假绿 | 断言写在永远走不到的分支上；或「一个红一个黄」却说成「都拒了」 |

**教训（已写入评审纪律）**：交付物是验收语料时，「规范坏了测试还绿」本身就是阻断级问题；销账要能说明**拆掉保护后测试会红**，而不只是「现在跑通了」。

### 2.3 内核语义上踩过的

- **版本钉太死 × memo 频繁合 main**：评审票钉死某次 base/head；memo 一合 main，旧票作废 → 重审风暴（安全，但贵）。后有 memo 批合纪律 + 窄 carry（非语义前进可继承绿票）。  
- **改 assignment 注释也改 blob**：义务 ID 全换，旧票对不上新债。  
- **归因靠人脑抄邮箱**：抄错 bot、串席；多 worktree 若共用一份本地配置会互相覆盖。  
- **cutover 边界**（在途 dogfood）：历史配置读不懂时若当「非 active」会**扩大认账或藏翻转**；只靠 tree 相同挂 merge 会**把后债错记成 cutover 前**；不是所有债都能降级成 warning——冻结面只授权一类（未登记 merge）时，别把别的债一并放行。

### 2.4 评审过程上踩过的

- **「关了」各说各话**：作者以为修了标题上的例子就算关；precision 看不变量邻域；spec 与 precision 同 head 一个 APPROVE 一个 RC。  
- **Finding 从不变量缩成例子**：长文有完整条件，评论一压缩就只追例子。  
- **一个 assignment 既「可并行起草」又「合入要等 kernel」**：结构上的 `needs` 和散文承诺打架。  
- **一轮修不完还横向加单**：后有 round 预算与 ESCALATED 上提用户。

### 2.5 产品层一句话

我们主要发现的不是「模型不够聪明」，而是三件事叠在一起会放大：

1. **没过审也能合** → 评审变债；  
2. **测试绿 ≠ 规则成立**；  
3. **版本钉死 × 分散合 memo × 关闭标准不一致** → 重审税。

## 3. 护栏：谁在执行？（人话）

本仓用执行等级（D-17）：**结构上难违反 → 命令直接拒绝 → 只告警可审计 → 靠自觉和流程**。

### 3.1 软件会管的（走 `hctl` 时命令会失败）

- 该过的评审没过 → **`hctl merge` 合不了**  
- 事实不完整、严重审计债（error）→ **claim / verdict / merge 等写操作拒绝**  
- claim 过期、不是 coordinator、base/head 对不上、配置钉变了 → **拒绝**  
- 席位配置非法、分支规则冲突 → **加载失败**  
- 归因工具链：邮箱解析、他席 bot、本地 seat 错配、按 worktree 隔离、离线可用 → **用工具时会校验**  
- 计票与（已合入的）carry 谓词 → **derive 机械算**  
- cutover 相关逻辑（以是否合入 main 为准）→ **状态机在代码里**  

语料/单测的「杀伤力」：写好了并且跑了，**回归时机械**；没人跑测试就合 PR，测试帮不上忙。

### 3.2 软件不怎么管的（文档 + 习惯）

- 谁提的问题只能谁宣布关闭  
- 两边审完先对唯一清单再改代码  
- 一轮只推一次、改不完上交用户  
- memo 先开 PR 攒着批合、作者评审期间冻结 tip  
- 销账要原反例 + 相邻改动 + 拆守卫必红等「证明关闭」  
- 「任务是人发起的」——配置里可写声明，**程序证明不了是真人**  

**没人执行 ≈ 没有。Activation 不会 magically 变成自动警察。**

### 3.3 半吊子（最容易误会）

| 你以为 | 实际 |
|---|---|
| 没过审就不能合 | **用 `hctl merge` 时**是；直接 GitHub/`gh` **现在还能绕** |
| 改 `.hctl` 必须别人审 | 代码里**正式运行（active）之后** `hctl merge` 才认真卡；**bootstrap 仍开口** |
| 测试防假绿 | 测例 + 评审要求；不是常驻守护进程 |
| 邮箱不能抄错 | 用 `hctl trailer` 会拦；**手写 commit 照样能抄错** |

**保证绑在「用不用 hctl」上，不是绑在「GitHub 上一切写操作」上。**  
设计选择：防手滑和漂移，**不防有权限的人故意绕**（与 README 一致）。

## 4. Activation 到底改变什么（仍用人话）

**现在（bootstrap）**

- 正经走 `hctl`：很多门已经在拦；  
- 仍允许图方便：自开自合例外、协调有时靠记忆和文档；  
- 历史上乱 merge 的债会卡写入 → 所以要先 cutover 认账，**不能直接通电**，否则可能「更严地谁也写不了」。

**Activation 之后（设计意图）**

- 配置进入正式运行：bootstrap「先方便着」的例外**按规矩结束**；  
- 再用 `hctl merge` 动关键配置时，**更难不经评审混进去**；  
- **不会**变成：网页合不了、人不用对账、评审社会学全自动化。

更短一句：

> **通电 = 正式模式打开，图方便的后门按设计关掉一截。**  
> **不是 = 从此所有纪律都变成机器人强制执行。**

## 6. 通电前仍应盯着的（检查单，非新裁定）

1. cutover 双席收口并合 main——否则正式运行与历史债的关系仍不稳。  
2. activation PR：配置置 active + kernel 钉到具体构建；activation 自身要落在 cutover 语义里（避免「正式工具合不进正式配置」的死结）。  
3. 真机 `hctl doctor`：bootstrap 例外、pin、远程跟踪等——口头说关不够。  
4. 合 cutover 后：旧未登记 merge 应是可写的告警认账，**新债仍要拦**。  
5. 评审 ownership / 预算仍靠人——active 后若继续靠记忆，扯皮会复发。  
6. adopters、session 证据自动取模型名等仍是后话——**通电 ≠ 功能做完**。

---

## 7. 收束

1. **问题侧**：最大的三类是「没过审就合」「测试假绿」「版本钉死与流程不同步」；归因串席、cutover 边界、关闭标准打架是具体 realization。  
2. **护栏侧**：**不是全散文，也不是全代码**——协作核走 `hctl` 时已经大量硬拦；评审社会学和「别绕工具」仍是工作方式。  
3. **Activation**：**关掉 bootstrap 图方便的一截**，不是承诺全自动执法。

本文供用户 activation 前讨论用；具体是否通电、门禁勾选，仍由用户裁决。
