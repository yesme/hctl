## 2. B 组逐条

### B1 obligation id — **同意（附钉死项）**

合流键 `hash(assignment_revision, kind, target_key, aspect)` + head 永不进 id + 按 kind 分岔 stale：

- **消解一审噪声担忧**：是。gate 的 `head_at_claim` stale 回池，不必每 push 铸新 id；claim/handoff/escalate 史可按稳定 id 聚合。  
- **codex 两条诉求**（在 27d 转述下）：assignment 变 → revision 变 → 新 id → 旧 claim 死；旧 verdict 不可复用由 B2 exact `{base,head}` 保证——**不依赖 id 含 head**。同意此安全性分离。

**必须钉死（否则新攻击面）**：

1. **`assignment_revision` 规范化输入**  
   27d 写「blob OID」又写「`{commit, path, blob}` 钉死」——二义。  
   - **攻击**：两份不同 path 的 assignment 内容相同 → 仅 hash(blob) 则 **id 碰撞**，claim 串台。  
   - **要求**：id 材料必须含 **path（或 assignment 稳定名）+ blob**；静态是否再含 tree/commit OID 由 P0 选一种并写进 schema 例子。动态 ASSIGN 用 event commit OID 无此病。  
2. **`aspect` 闭集**  
   multi-gater 并行仍靠 aspect（一审 ⑪c）；P0 写死如 `gate:<seat>` / `author` / `merge`，禁止自由字符串当路由。  
3. **assignment 死后的 id**  
   CANCEL/删文件/ supersede 后，旧 id 的 claim/verdict 必须 derive 为 dead target，写动作拒绝——不只「新 revision 新 id」。  
4. **hash 算法与截断**  
   指定（如 sha256 全长或固定前缀）入 schema，禁各实现私自截断导致碰撞策略分叉。

**新攻击面（可接受但要写）**：assignment 文件被「无语义空白变更」→ blob 变 → 全员 claim 作废 = **合法 re-gate 风暴**。doctor/status 应亮「assignment_revision moved」；对 assignment 路径的 PR 建议 required gate + 低 churn 纪律（级④点名即可）。

### B2 base freshness + merge-as-obligation — **有条件同意**

#### 定向问 1：严格 base 摩擦账 + 攻击「先严后松」

**量级估算（对抗账，非测量）**  
假设 dogfood：日均 **2–5** 个在飞 required-gated PR；六席双机不线性放大 re-gate 次数（义务在 PR/assignment 上，不在化身数上）。

- 严格规则：每次 **main 前进一次**，所有 **base ≠ 新 main tip** 的在飞 required verdict **全体 stale**。  
- 若 k 个 PR 依次 merge，且期间其余始终在飞：re-gate 触发次数上界约 **1+2+…+(k-1) = k(k-1)/2** 次「至少有一席要重审」事件（不是 k² 席次，是义务次数）。  
  - k=3 → ~3；k=5 → ~10；k=8 → ~28。  
- 单次 re-gate 成本：K-15 热上下文 delta 复审 ⇒ **远低于冷启动全文**；但若 holder 不在线 / claim overdue 换手，成本跳回冷。  
- 双机：只增加 CLAIM 竞争，不增加「法律上要审几次」。

**结论**：在 **k≲5、串行 merge、author_concurrency=0/1** 的本仓信任模型下，**摩擦可接受**，用吞吐换确定性值得。超过 k≈8 的并行 merge train 会痛——那是产品压力信号，不是现在放宽的理由。

**攻击「先严后松」路径本身**：

| 攻击 | 说明 | 要求 |
|---|---|---|
| 习惯锁定 | LLM/人学会「base 一变就重批」；日后 tracking-base 放松 = 静默语义变更 | 放松必须 **schema `v` / DECISIONS supersede**，status 自描述写清规则代际 |
| 痛苦驱动偷松 | 未语料先开旋钮 → K-05 旋钮最少化破产 | P3 前 **禁止** 配置项；仅 METHOD「未来项」一段 |
| 社会疲劳 | 频繁 re-gate → 橡皮图章 APPROVE | 审计级③：短间隔重复 APPROVE 同 head 可黄灯；不入自动通过 |
| merge 列车抖动 | A merge 使 B stale，B re-gate 间 C merge 再 stale | merge-as-obligation 串行化 **减轻但不消灭**（见下） |
| 策略绑死 | 消费仓若不用 squash / 乱改 base | adopters **钉 squash**；非 squash = `UNJUDGEABLE_MERGE` fail-closed（一审⑤） |

**`gh pr merge --match-head-commit`**：本机 `gh` 已证实有该 flag——B2 技术前提成立。

**有条件点（merge 授权缺口）**：  
merge-as-obligation 闭合 TOCTOU 的 **互斥半边**（同时两个 merge claim 抢 main），但未写：

- **谁可以 claim merge？** author？任一 required gater？quorum 已齐的任意席？  
- 若「任意席可 claim merge」→ 与 B4「不自造义务」尚可（义务由 assignment 导出），但可能 **抢跑 merge**（advisory 未齐时——应由 derive 在 claim/merge 时查 quorum，级②拒绝）。  
- 若仅 author → 经典 self-merge；须 gater≠author 已在 verdict，merge 另需「quorum green」硬门。

**要求 P0 一句**：`claim(kind=merge)` 前置条件 = derive 见 required quorum green（对 exact `{base,head}`）且无更高优先级阻塞；merge wrapper 内二次 re-check。满足则 **同意 B2**。

### B5 fencing claim-OID — **同意（弃 epoch）**

一审 epoch 诉求是防脑裂，不是恋整数。claim-OID + `reclaim_of` + 完成类事件引用 active claim = **同构且更 git-native**。

附形态要求：

1. **首 claim**：`reclaim_of` 缺省/null；derive 认「无 active claim 时可创建」。  
2. **re-claim**：必须 `reclaim_of == 当前 active claim OID`；push CAS 决定赢家。  
3. **HANDOFF**：27d 只说完成类引用 active claim——须补：**HANDOFF 是否原子转移 holder（推荐：HANDOFF 事件本身结束旧 claim 并隐含/内嵌新 claim OID）**，避免 release 窗口双空。  
4. **VERDICT 引用 claim OID** 且 claim.obligation_id 匹配、claim 未 stale——级②。  
5. 展示层「第几代」= 链上该 obligation 的 CLAIM 次数——OK，不进协议。

### 定向问 2：C9 + B5 是否闭合 ⑪b 震荡

**闭合自动震荡：是。闭合恶意/糊涂双主力互抢：升到「可观测 + 人裁决」，不再是静默活锁。**

- **永不自动 re-claim**：杀掉 watchdog/心跳式抢锁——与 K-06 一致，本堂支持。  
- **claim-OID `reclaim_of`**：双化身同时 re-claim 同一 active → 一人 push 赢，另一人 non-ff；赢家 OID 变，输家再推必须改 `reclaim_of`——**无双活持有**。  
- **≥2 次 re-claim / 窗口 → 红灯 + escalate**：对称踢皮球会变成 **escalation 风暴**（人可见），而非无限链上 CLAIM 而无升级。  

**仍未钉死的边角**：

1. **「窗口」定义**  
   墙钟？assignment 生命周期？active claim 世代链？  
   - 若墙钟过短：长任务合法 touch/re-claim 误伤。  
   - 若从不清零：一次事故永久红灯。  
   - **建议**：按 **obligation_id 计数**——同一 id 下 CLAIM 事件数 ≥2 且 **无 interleaved 可验证进度**（head 前进 / VERDICT / memo 合入）⇒ 红；有进度则计数可重置或降黄。避免纯墙钟心跳。  
2. **双主力仍可能每人成功 re-claim 各 1 次**（共 2 次）才红——可接受；模板非对称 standby 降概率。  
3. **escalate 之后** 义务态：冻结 claim？回 unclaimed？须 P0 一句（建议 **frozen until user CANCEL/ASSIGN**）。

满足窗口/进度定义后，**⑪b 对抗关闭到可实现级别**。

### 定向问 3：B1 + head_at_claim 与 re-claim 噪声

**是，消解一审主噪声路径。**  
新噪声改为：

- assignment_revision 抖动（见 B1）；  
- 严格 base 导致的 **verdict** 重做（B2，不是 claim id 爆炸）；  
- gate head 前进 → claim stale → **一次** re-claim（期望行为）。  

整体优于 head-in-id 的每 push 新义务。
