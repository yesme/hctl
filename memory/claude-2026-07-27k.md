> 性质：用户质询定案记录。裁决原话「我总感觉『可靠席位』这种说法非常不可靠——事实上所有的席位都犯过错……有没有机械化的方法来执行这个动作么？」+「对。收口。」

## 1. 质询与改判

用户指出「可靠席位」是级④思维复辟——D-17 第一原则（违规是设计问题不是品行问题）要求的正确问法是：**动作还剩多少非机械成分，降到零**。主笔承认此前用「席位品行」选 coordinator 的框架错误。coordinator 在 hctl 落地后的残余人为动作逐项可机械化：

| 残余动作 | 机械化 |
|---|---|
| 发现绿灯并调用 | timer 定时跑 `hctl merge --auto`——**timer ≠ daemon**：每次触发是叶子命令做全量 reconcile，漏跑无害下一跳补齐（D-02 level-triggered 教科书应用；被废除的是有状态心跳侧车，不是定时点火） |
| merge train 排序 | 确定性规则进二进制（quorum green 时序 / assignment id 序） |
| 红灯处置 | 本就只许 escalate：退出码 + 通知，上报对象是人 |
| 持锁的链 | 链只需身份归因，不需智力——coordinator 席 harness 终态可为 `cron`；merge 路径 LLM 连选择题都没有 |

**终态：merge 执行者不是 LLM 席位**。「哪个席位可靠」的正确答案是「没有席位」——K-17「最强执行是删规则」的孪生句：**最可靠的席位是把席位从回路里删掉**。AGY-as-coordinator 之问随之蒸发。

## 2. 阶梯（转录 D-37 补遗）

1. **P1（现状）**：claude 席化身手动 `hctl merge`——人为成分只剩按回车，receipt/CAS/post-verify 全在二进制。
2. **P1.5**：timer 跑 `hctl merge --check --notify`——机器发现+验证，扣扳机仍是人/任意席位；观察期攒 receipt 审计记录。
3. **P2**：corpus 全绿 + 观察期无异常 ⇒ 切 `--auto`，LLM 全部出回路；每级切换=一次 config 变更（rebind 机器 D-37/F3′ 现成）。

风险账（诚实）：全自动下 hctl 的 bug 会无人眼合错——护栏三件：receipt+post-verify 错误响亮、`UNRECORDED_MERGE` 审计抓旁路、corpus 是准入门槛（故排 P2 不排明天）。凭据零新增（gh 凭据本在机器、单账号模型）。授权不变：权威=quorum green（推导），ASSIGN/CANCEL 仍人发起（D-38）。
