## 1. 结论（K-31 提案，待用户裁决）

**事件层基质 = per-seat event commit chain**：每席一条线性 commit 链（`refs/coop/<seat>`），一事件一 commit。弃 git notes。

审题②三堂**独立同判**：本席（通读+实证，本文）；codex（「选 custom event commit chain」，并自做 CAS 最小实证，[codex ②/⑪-A](codex-2026-07-27.md)）；grok（「倾向裸链，notes 作否决项除非证明 CLAIM 友好」，[grok ②](grok-2026-07-27.md)）。grok 要求的选型判据「是否便于 epoch CAS 与 checkpoint」本文 §3/§5 落实；grok 认定的通读义务本文 §2 结清。

git-appraise 遗产按 K-20 拆解继承：**先例**（review 元数据全放 git objects/refs、零服务端——上层判断成立，refs 事实源直接先辈）+ **schema 纪律**（§6 清单）；其 **notes 存储形态不继承**（§3B/§4 死因）。链形态的业界先例=Gerrit NoteDb per-change meta ref（每 change 一条元数据 commit 链、ff-only 同步）——我们已在 patchset/submit-requirement 上对齐 Gerrit，基质继续对齐。

## 2. git-appraise 通读实录

基本面：四条 notes ref（`refs/notes/devtools/{reviews,discuss,ci,analyses}`）；一条 note 按行放多个自包含 JSON（git.go:919-923）；有正式 JSON Schema（`schema/*.json`，draft-04）；多写者同步 = fetch + `git notes merge -s cat_sort_uniq`（git.go:1056、1177）。

五条对选型有决定量的发现：

1. **他们在与自己的存储层打架**（request.go:37-39 注释原文）：timestamp/author 是「optimization」反规范化进 JSON——因为从 notes 历史推导作者/时序要对 notes 对象跑 git-blame，「随 review 规模越来越贵」。链上这两样白送（commit 元数据 + 拓扑序）。他们的 workaround 本身构成链的论据。
2. **timestamp = 10 位零填充 epoch 字符串**（comment.go:161-174；schema pattern `[0-9]{10,10}`）：零填充唯一动机=字符串可排序——notes 树序=被注解对象 SHA 序、与时间无关，时序只能靠内容时钟重建。链的时序=拓扑序，零时钟依赖。
3. **可达性要自己造**：notes 不使被注解对象可达；appraise 专门造 `refs/devtools/archives/reviews` 平行链（git.go:389-417，commit-tree 多亲缝合）防被审 commit 被 GC。hctl 对应物 = `refs/pull/*/head`（GitHub 保留、K-18 监听面已含）；archive-ref 手法记档，作脱 GitHub 场景备用件。
4. **并发模型=union**：cat_sort_uniq 把并发写合成并集；git.go:1177 注释明说「git-appraise schemas fit that requirement」——schema 特意设计成合并友好。对评论集合正确（两条评论都该活）；对 CLAIM 致命（两个认领只能活一个，§3B 实证）。
5. **宽进严出已有实现先例**：`ParseAllValid`（request.go:86-95）静默跳过版本/形状不符的 note、容忍异构流——K-03 的既有形态。

另一条进 P1 实现纪律：批量读=3 次 git 调用（notes 清单 + `cat-file --batch` 过滤类型 + batch 取内容，git.go:880-928）——**禁止 per-object exec、一律 batch plumbing**。

## 3. 沙盘实证（可复现形态见 `tests/corpus/concurrency/`）

**A. 链上 CLAIM 双层互斥成立**：
- mac 发 CLAIM（commit → `update-ref` → push）成功；
- ubuntu 同窗口竞争 CLAIM，push 被拒 `! [rejected] (fetch first)`，远端 tip 不动；
- ubuntu 对账让位（CAS 复位到远端赢家）后续发自家 VERDICT 成功，链保持线性；
- 同机双 tab：第二写者被 `update-ref` CAS 挡出（`fatal: … but expected …` 响亮失败）——K-30 双层原子第一层；
- 读路径=一条 `git log`，全事件精确拓扑序。

**B. notes 官方路径破互斥**：双化身各 append CLAIM note；后推者被拒（到此与链同性质）；但走官方冲突处理 `notes merge -s cat_sort_uniq` 后 push 成功——**两条 CLAIM 并存于同一 note**。互斥不是被实现而是被合并策略合法性消解；若改用内容 timestamp 裁决则退回跨机时钟比对。K-28 的 push-mutex 前提在 notes 下不成立。

codex 独立做了同构实证（同 clone 双候选 `update-ref` 一成一败 status 128；双 clone push 一成一败），两组实验互相印证；语料即两组手工实验的可断言化。

## 4. 判据表（浓缩）

| 判据 | event commit chain | git notes |
|---|---|---|
| CLAIM 互斥 | ref CAS + push 拒绝 = K-17 级①/②物理 | 官方 merge=union，互斥被绕过（实证 §3B） |
| 时序确定性 | 拓扑序，零时钟 | SHA 树序，靠内容时钟重排（跨机 skew） |
| 事件锚点 | 六类同构（revision 是 JSON 字段） | 4/6 事件（EDGE/CLAIM/HANDOFF/NOTE）无自然注解对象 |
| 读路径 | 单 `git log` / batch | 3 次 batch（appraise 自身的规模优化） |
| 可达性 | 事件「命名不引用」SHA，靠 refs/pull | 同；appraise 为此建 archive-ref 子系统 |
| 业界先例 | Gerrit NoteDb meta ref | appraise（review 锚定场景，非分布式锁） |

notes 仅存的两优势均被既有定案抵消：per-commit O(1) 查询 ← K-02「每次调用即全量 reconcile」本就全折叠；`git log --show-notes` 人读 porcelain ← K-13 自描述 status 替代（GitHub 网页 2014 年后亦不渲染 notes）。

三目标记分：**确定性**——链胜（拓扑序零时钟、冲突=响亮拒绝、审计=`merge-base --is-ancestor` 线性检查+schema 校验，全部脚本级）；**网络**——平手（两者均纯 git transport 零 REST，K-01 红利不变；链增量 fetch 略瘦）；**LLM**——链胜于失败模式（非 ff=让位重试可脚本化；notes 冲突要么 manual merge 要么 union 后语义修复，都会请回判断）。

## 5. 三堂汇流与本席改判

**一致（可直接进 DECISIONS）**：
- ② 弃 notes 取链，三堂同判；
- appraise 按「先例+纪律」拆解继承；
- 「所有事件一律钉 head」不成立（本材料锚点分析、codex ⑥-C/⑩-1 同向）→ 修正为「**revision 依赖型事件必钉 {base, head}**」。

**本席改判两处（吸收 codex 精密堂）**：
1. **payload 位置**：原实证用「空树 + JSON in commit message」；改判采 **tree 含单文件 `event.json`、message 放人读摘要**。理由：payload blob OID = 内容寻址的事件身份（appraise `comment.Hash()` 的 git 原生形态，免自定义规范化哈希）；batch 读走 `cat-file` typed 对象，无 `%B` 分隔符解析边角；message 摘要保留 `git log --oneline` 人读性（K-13）。原「对象数 1 vs 3-4」论点在实际体量下无差别，放弃。
2. **push 升级为显式 lease**：`git push --force-with-lease=<ref>:<expected-tip>`（创建用空 expect=「必须不存在」）替代裸 push。裸 push 只保证单调（ff），**检测不了远端回卷**：链被回退到祖先后，裸 push 会把回卷无声「修复」；显式 expect 使回卷=push 失败=完整性红灯（K-17 响亮失败；codex ⑪-A 同判）。语料已按此形态实现。

**留给 P0/用户的分叉（两堂方案对照；本席不在本 memo 抢裁）**：
- **obligation id 代数**：grok 案=稳定键 `hash(kind, target_key, aspect)`、head 不进 id、按 kind 分岔 stale（[grok ⑪c]）；codex 案=assignment-revision 锚定、gate id 含 `{base,head}`（head 动=新义务，[codex ⑥-B]）。两案殊途同归于「head 变化使旧 claim/verdict 不可复用」，代数不同（id 稳定性 vs re-claim 噪声）。
- **fencing 机制**：grok=单调 epoch 整数；codex=claim event OID 作 fencing token（git 原生、无计数器）。
- **ref 命名与 publishing/tracking 分离**：codex 案 `refs/hctl/remotes/<remote>/events/<seat>` 独立追踪 ref；「发布 ref ≠ 追踪 ref ⇒ 有未决发布」。方向认同；`refs/coop` 更名与否属 K-01 用户裁范围。
- **幂等身份**：codex 的 `event_id` UUID vs blob-OID 查重（byte-identical 重试天然同 blob，前提=pending commit 即本地日志）。P0 定一种。

## 6. 采纳清单（进 `event.schema.json` 的 appraise 遗产）

- `v` 整数版本字段，enum 钉死（appraise `FormatVersion` 同形）；
- `timestamp` 10 位零填充 epoch 字符串，pattern 连同抄入——链不靠它排序，但**双时戳互证**（JSON ts vs commit date）是白送的级③审计位；
- 宽进严出 parser 形态——与 codex「坏事件 quarantine 整链」在 P0 调和为两分法：**结构坏（非线性/非单 parent/非法 JSON）= quarantine 整链；语义未知（新 type/新版本）= 跳过（前向兼容）**；
- `original` 修订指针（append-only 下的事件修订，NOTE 修订用）。

**明确不抄**：`alias`（追踪 rebase 后 commit——K-04 stale-on-head-move 的反模式）；`gpg.Sig` 暂不采（护栏防失误不防恶意，schema 留 `sig` 保留字）。

## 7. 经济学落账（目标②③）

事件全程 git transport，**零 REST、不吃 API quota**；gh 维持 `pr create`/`pr merge` 两条（K-01 红利不变）。wake 的 30s `ls-remote` ≈ 2880 次/天/等待循环、每次 ~KB 级 info/refs 广告——量级无害，但 codex ④ 的 clone 级合并轮询（一 clone 一 poll leader、其余读快照）应进 P2 规格。链体量上界：6 席 × 100 事件/日 × ~500B ≈ 全仓年增 ~110MB（重度假设，实际远低）；P1 用 tip-keyed 可丢缓存做增量读；无数据前不设计 compaction（codex ①同判；grok G1/G2 站队待真实数据）。
