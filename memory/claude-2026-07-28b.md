## 1. plan/build 的本质不同

各家 harness 的 plan/build 二分（Claude Code plan mode、Cursor Ask/Agent、Aider /ask-/code、Copilot Workspace spec→plan→implement）同源于四个压力：不可逆边界、人注意力经济（审几百字意图便宜、审几千行 diff 贵）、漂移控制（plan=压缩检查点+执行锚）、并行化前提（冻结的分解才能扇出）。抽象掉 UI：**用一个可检查的冻结物，把意图的形成与意图的执行隔开**。

但更深一层（用户点破、本席精化）：

- **build 在既定评价函数下求解；plan 在构造评价函数本身。** 评价函数尚不存在，故无「验收」可言。
- 精确化：plan 面**只可证伪、不可证实**（Popper 不对称）——方案可被一个反例杀死（本仓实证：patch-id、tree-equality、「只会收紧」皆亡于反例），但 build 出来前无法证明为对。plan 面最佳质量机制是**征集反例**，不是验收。
- **收敛的位置**：build 的收敛压力内在且连续（每步朝冻结目标）；plan 的收敛被**显式推迟并外置**给一个权威时刻（resolution）。中间必须保持不收敛——无 oracle 时，多样性是唯一的质量来源，过早收敛=信息销毁。
- **分歧的地位**：build 里分歧是缺陷（要 reconcile 掉）；plan 里分歧是产品（要保护住）。「independence」在两面含义相反：build 的双 gate 是冗余防漏检，plan 的双贡献要**正交**——相同观点是零信息。
- **关闭的性质**：build 靠证据销账（owner+proof）；plan 靠权威裁决（resolver）。两种「关闭」不可混：能授权下一步的就不是 advisory memo（codex #80 同判）。
- **多席形变**：单席 harness 里 plan/build 是时间交替（一个脑子换挡）；多席协作里是**空间并存**（codex build kernel 时 claude/grok 在 plan 下一轮）。「模式」必须变成「面」（plane）：一个永不停的 plan 面 + N 个并发 build 执行体。plan/build 还是**分形的**——每个 build 内套 micro-plan。

**推论：build kernel 的全部机制都是反发散机器**（exact revision、freshness、单一规范执行者、owner-only closure、round budget、fencing、D-34 阻尼惩罚 non-forward），搬进 plan 面是有害的范畴错误。plan kernel 需要每件的对偶物：

| build 面 | plan 面对偶 |
|---|---|
| 冻结 revision 钉代码 | 冻结**输入快照**（各席贡献 OID），不判内容对错 |
| gate 验收、RC 阻断 | 贡献**不设 gate、永不 RC**；反驳欢迎但不阻塞 |
| owner 销账 | resolver 裁决 |
| 阻尼惩罚不前进 | **保护不收敛**：贡献期无同意压力、veil 隔离 |
| merge slot 串行化 | 一场讨论只归档进 main 一次 |

memo「即开即合 vs 等待」之争由此见底：那是在问「这个 PR 何时 merge」，但 memo 根本不是 PR——它是贡献物，生命周期为「草稿→按 veil 策略可见→冻结为输入→随 resolution 归档一次」。用 build 面的运输工具（main 线性历史）承载 plan 面话语，才制造了这个伪问题；batch/carry 只是减震器。

## 2. 现实拓扑：以用户为总线的星型网络

实践观察（用户描述）：每席与用户保持**双边、私有、持续**对话（chat，账外），沉淀 memo（落账）；席间默认无信道，跨界仅在用户说「去读」时发生。原语四个：**说 / 写 / 读（跨界）/ 转发**（让 xxx 和 yyy 去读、你收反馈）。两轴：读的范围（某席最新/全体最新——「最新」蕴含 per (读者,来源) 的**游标**）；谁去读（用户切 tab 直令 / 委托某席转发）。

三个设计后果：

1. **独立性是默认态，不是待建机制**——不需建墙，只需**记门**：跨界读经工具走则在读者链上留 {谁,读了谁,读到哪个 tip} 事件，每篇 memo 的「信息基础」可重放（plan 面版 state=derive(git facts)）。凡跨界必留痕后，未留痕即独立性声明，落诚实阶梯级③/④。「读全体最新」即冻结快照（frozen_inputs）的雏形。
2. **转发模式 = 胚胎态 synthesis 委托，今天缺传输层**——席 A 无法「让」B 读，现实靠用户人肉摆渡。补法为现成模式：**level-triggered read-request**——A 留请求事实，B 下次 status 看到（唤醒宽进、漏醒无害，D-02 复用；亦是 obligation 状态机轻量版，支持同构方向）。转发席持有**压缩权**——R3 教训（转述退化）在 plan 面的镜像；frozen_inputs 钉原文 OID 让 synthesis 可对照未压缩原料审计。
3. **chat 账外 / memo 落账的边界是特性**——可被他席取用的恰是作者有意外化之物。不共享 chat，只把「发表」做便宜。

plan kernel 最小起步集 = **流 + 门**：每席 append-only memo 流（durable ref、不进 main）；带游标的跨界读事件；read-request；讨论 id 仅作话题作用域（十席时「读本讨论内全体最新」才有界）；synthesis/resolution 仍为权威动作。

## 3. 席位模型

**生命周期**：① 开 harness 得 TUI → ② AGENTS 发现规约、`hctl seat` 查绑定（有则续、无则绑）→ ③ **对表**：`hctl status` 推导本席所欠/所等/被请（session 无需记忆，醒来全量 reconcile）→ ④ **取活**：工作仅两源——用户的话（未冻结意图，plan 面）与冻结契约（obligation，build 面）→ ⑤ 做事：留痕动作过 hctl，事件带 {seat,machine,session} → ⑥ **死亡无仪式**：durable 全在席位资产，session 只有易失工作记忆，claim 有 timeout 兜底。

**Seat = session 的可持久投影**，四个去重单位：

1. **一票**（quorum 同席一票）——席位是「视角」单位，session 是「吞吐」单位；多席的意义是判断去相关，同 type 多 tab 高度相关，各计票=重复计票。
2. **一个署名**（bot 归因席级，tab 只进审计字段）。
3. **一条独立流**（memo 流+事件链+游标皆 per-seat 单链；席内多 tab 抢活用本机 CAS，家务事不上协议，D-36）。
4. **连续性本身**——协作里的「人」是 seat，session 是这个人的一次次到场。

**快问快答定案**：

- 席位 = **harness_type × repo**：某 type 在某仓宪法（seats.toml）里的公民身份（户口），授权皆仓内；同 harness 在两仓=两席。
- harness_type 身份分层：**身份键=harness**（model 编进身份则每次升级=换人、链断代）；**model=席位声明属性**（seats.toml 入册、gated 变更、doctor 可审——quorum 的多样性假设依赖它，两席悄悄同模型应亮灯）；**effort=逐会话实况**（只进 trailer/actor）。类比：席位是职位名，模型是现任者版本号，effort 是今天的精神状态。
- 多 tab = 同一席位（绑定相同时）：一票、共享 claim、本机 CAS 分胜负。边界：同 type 同仓开两席物理可写但等于给同一判断分布发两票——**开席是治理动作**（gated `.hctl` 变更，ASSIGN 级），不是 init 级；绑定既有席（`seat init`）才是本地动作。TUI 启动遇「无此席」的正确行为是提示入仓需授权，不是静默创建。

## 4. 收束主张与留给 resolution 的问题

**协作 = 有纪律地发散 + 有权威地收敛 + 有契约地执行。** P1 已把第三段造成钢筋混凝土（build kernel + activation 通电在即）；本轮讨论暴露前两段还住在帐篷里。P2 的主题应是 **plan kernel**，且按 D2（双权威必分叉）：不做第二套系统，做**同一状态机的新 kind**（discussion 之于 assignment 同构，复用 freeze/CAS/quorum AST/round budget；本篇 §1 对偶表给出各机制的方向变换）。TUI 语义定义随之钉死：**前台=plan 面端口（权威注入+未冻结意图的谈判桌、「不收敛合法」之地），后台=冻结契约的执行池**；前台的话不算数，直到过冻结边界。

留给讨论/resolution：

1. plan kernel 的硬护栏是否只有「独立性」（记门+快照+归档完整性）？**出题权**（谁能开讨论、框什么问题——框架即权力）是否也需结构约束？现状出题权全在用户手上，可能恰好掩盖了它的设计难度。
2. 用户路由（模式①）线性消耗用户注意力，委托转发（模式②）消耗信息保真度——席位规模化时先补哪个？
3. 与 codex #80 的收编关系：其 outcome_contract/状态机/§5 memo 脱 PR 与本篇方向一致；建议 resolution 时以「同构 kind」框架收编（contribution 无 gate、resolution 权威关闭两点为本篇的硬约束输入）。
4. 席位 model 属性的 doctor 检查（两席同模型亮灯）是否入 P2 范围。
