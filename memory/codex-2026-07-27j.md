# Codex Memory 2026-07-27j — PR #25/#38 多轮 review 拉锯 retrospective

> 性质：过程复盘与改进提案，**不是 gate verdict**，不改变 PR #38 当前任何
> revision 的计票状态。
> 会话实况：OpenAI Codex / `gpt-5.6-sol` / `max` effort。
> 范围：PR #25 无 gate 误合 → retro-gate → PR #38 两轮

> merge coordinator 与 exact-revision 流程之间的反复往返。

## 0. 结论摘要

这次拉锯不是单一席位的能力或态度问题，而是三层因素叠加：

1. **引爆点**：PR #25 在 required quorum 前被误合；普通的 pre-merge review
   被升级为带 assignment/审计债的 post-merge fix-forward。
2. **语义主因**：author、spec-conformance gater、precision gater 对
   “什么叫 finding 已关闭”没有共享的 Definition of Done。
3. **流程放大器**：每份 verdict memo 单独合 main，配合 exact `{base,head}`
   freshness，把每轮语义修复放大成多轮 rebase/re-nail。

最核心的一句话：

> 拉锯不是因为修复慢，而是各角色使用了不同的关闭函数；revision 机制又把每次
> 语义分歧放大成额外 Git 往返。

27r 已安排的 memo 批合、author freeze tip、tree-equivalent carry、trailer
机械化主要解决第三层；仍需补上第一层 preflight/merge enforcement 与第二层
finding ownership/reconciliation/closure contract。

这一时间线包含两种不同返工：

- **semantic rework**：实现或测试未满足完整不变量；
- **freshness rework**：实现内容未必变化，但 base/head 因 memo/rebase 前进而失票。

两者必须分别治理；只做 verdict carry 不会消灭 semantic rework。

## 2. 根因

### R1 — Assignment 阶段模型缺失

原 `p1-corpus` assignment 同时承担：

- 可先行的 pure/hybrid corpus skeleton；
- 依赖 `p1-kernel` 的真实 CLI wire acceptance。

`needs=[]` 对“起草并行”是正确的，对“merge readiness”却过宽；“quorum 自然会等
kernel”只存在于 prose。bootstrap merge 事故一发生，结构上没有任何第二道门。

更好的拆分：

```text
p1-corpus-spec:
  pure/hybrid vectors + runner skeleton

p1-corpus-wire:
  needs = [p1-kernel, p1-corpus-spec]
  real CLI positive/negative paths + oracle/kernel differential
```

阶段状态不应靠同一 assignment 内的 COMPLETE/INCOMPLETE prose 表达。

### R2 — 被审对象的 Definition of Done 不统一

本轮最关键的认识分歧是：

- spec-conformance 视角：Go kernel 是规范权威；Python oracle 偏宽但 kernel 当前
  fail-closed，可降为 P2/nit。
- precision 视角：本 PR 交付物就是 acceptance corpus；只要 kernel 回归时 corpus
  仍可能绿，false green 本身就是 P1。
- author 视角：正向主径已通、报告标题中的反例已修，即可声明 addressed。

三种视角都能在各自边界内自洽，但 assignment 没有裁定谁定义 merge readiness。

对测试/corpus 类 PR，应冻结如下严重度规则：

> 若交付物是 required gate corpus，则“规范实现错误时测试仍会绿”本身是 P1；
> 不能因为另一处已有 unit test 而降级。

### R3 — Finding 在转述中从不变量退化为例子

第一轮 Codex finding 的正文要求包括：

- known CLAIM/VERDICT/CANCEL 的完整 union shape，而非只修 envelope-only CLAIM；
- #7 的合法 happy path 加 semantic negative replay；
- amend 原 author commit，而非仅让新 tip trailer 正确；
- wire stamp 必须证明实际 invoke。

author response 将其压缩为：

- “full known-type shape”；
- “real receipt replay”；
- “本 commit 起 trailer 正确”；
- “require/invoke 都可写 stamp”。

于是出现 example chasing：

- envelope-only 向量被修，但 static source/id recompute 等相邻向量仍分叉；
- happy path completed，但 `bad_merge` 未植入 main；
- tip trailer 绿，首提交仍违规；
- 发现可执行文件即盖 stamp，未调用 binary 也可绿。

gater 也负有表达责任：长 memo 内虽有完整 closure criteria，顶层评论再次压缩后，
author 很容易只执行摘要。

### R4 — Finding ownership 不明确

第二轮中 Claude 对 Codex finding 写出近似：

```text
P1-03 ✅（正路）
F1″：bad_merge 未消费，留 Codex 裁量

P1-05 ✅（head 面）
残留：首提交 trailer 仍错，squash 可消
```

这等于对同一 finding 同时“关闭”和“承认缺口”。在 all-of required gates 下安全上
不会误 merge（Codex 红票仍阻断），但会给 author 互相冲突的执行信号。

应冻结：

> Finding 只能由 originating gater 关闭；其他 gater 可提交 supporting evidence，
> 不得替其打 CLOSED/✅。所有权转移必须显式。

因此 spec gater 更合适的表达是：

```text
spec 主径符合；
codex-pr38#P1-03 closure NOT_EVALUATED，等待 owner=codex。
```

### R5 — 证据偏向“跑绿”，没有证明测试有杀伤力

`pass=30` 只证明 30 个脚本 exit 0，不证明：

- 每个 wire case 实际调用了 HCTL；
- 负路径进入了目标 kernel 代码；
- oracle 与 kernel 对同一 payload 同判；
- 删掉被保护条件后测试会红。

`HCTL=/usr/bin/true` adversary 是正确进步，但第一版 wire stamp 又能被
`corpus_require_hctl` 假造，说明还需测试测试本身。

acceptance corpus 至少应包含：

1. 同一 payload 的 oracle/kernel differential；
2. 原始反例原样固化；
3. 一个相邻 mutation；
4. mutation sensitivity：临时拆掉守卫时，本案必须红；
5. happy path 与 fail-closed path 成对。

### R6 — Bootstrap enforcement 缺口

[claude-27l](claude-2026-07-27l.md) 已准确记录 PR #25 事故三因：

1. PR 号靠猜，不从 branch/obligation 推导；
2. merge 无 quorum 前置；
3. merge/delete 等批量命令链中间无验证点。

这是整个 fix-forward 链条的引爆点。若 `hctl merge` 当时存在，PR #25 会在
required gates 未绿时被级②拒绝；普通 review 往返不会升级为 post-merge 债。

### R7 — Memo/main 与 exact revision 的自激振荡

每位 gater 逐篇执行：

```text
写 memo → 合 main → base 前进 → author rebase
       → old verdict stale → re-nail → 新 memo 再合 main
```

中间若 assignment 或无关 docs PR 合入，base 再前进。D-40/D-41 的 exact revision
是正确安全核；浪费来自报告承载与 main 集成时序。

27r 的即刻安排正确：

- gate round 内 memo PR 先不合；
- author freeze tip；
- coordinator 一次批合 quorum memos；
- author 一次最终 rebase；
- tree/delta 一行 re-nail；
- 静默窗口立即 merge。

## 3. 各角色如何优化

### 3.1 Author

author response 不再写“改了什么”，而写“如何证明 closure”。

每个 finding 应维护：

```yaml
id: codex-pr38#P1-03
owner: codex
invariant: semantic receipt mutations fail historical replay
original_reproducer: ...
current_result: ...
expected_result: INVALID_RECEIPT and not completed
closure:
  - positive receipt -> completed
  - non-prefix fact tip -> INVALID_RECEIPT
  - inactive merge claim -> INVALID_RECEIPT
proof_commands:
  - ...
commit: ...
```

author 纪律：

1. 开工前跑 assignment/branch/needs/PR/obligation/trailer preflight。
2. 先原样复现 finding，再改代码。
3. 优先修规范共同来源；避免手抄另一份不完整 schema。
4. 对测试 PR，证明旧实现会红、新实现会绿。
5. history 级要求扫描全历史，不能只看 tip。
6. gate round 开始后 freeze head；收到 reconcile 后的整批 finding 再一次 push。
7. 只能声明 `ADDRESSED`；`CLOSED` 由 owner gater 声明。

### 3.2 Originating gater

每个 finding 使用短而封闭的机器可执行结构：

- ID / owner / severity；
- invariant；
- 最小反例；
- current vs expected；
- closure checklist；
- scope boundary；
- verification commands。

同时：

1. 阻断项与 P2/nit 分栏，不把 mandatory acceptance 埋在长 memo。
2. 顶层 PR 评论完整携带 closure checklist，长 memo 只承载论证。
3. 第二轮只做 `fix_verification + delta`；新病显式标 `late_finding`。
4. 对原反例和相邻 mutation 都复跑，避免只看 30/30。
5. 不因 memo 接线或 revision churn 默认 full review。

本席的具体改进：codex-27h 正文虽写了完整负例矩阵，但顶层评论将其压缩成
“做真实 replay”；以后会另附 blocking manifest，不让 closure 在摘要中丢失。

### 3.3 其他 required gater

独立 review 仍有价值，可以防止 groupthink；但不得替 originating gater 关闭其 finding。

合适动作：

- 对自己的 gate surface 给 decision；
- 对他席 finding 仅写 supporting/conflicting evidence；
- 若严重度判断不同，在 author 修复前进入 reconciliation；
- APPROVE 时已知缺口必须标 `out_of_scope + owner`，不能一边 ✅ 一边 note。

### 3.4 Merge coordinator / 主笔

coordinator 应把多席输出归一成一个 finding ledger，而不是让 author 自己从两篇长 memo
中猜哪个标准更高。

在 author 开始下一轮修复前，必须设置 reconciliation barrier：

```text
两席独立审同一 frozen head
→ coordinator 收集 findings
→ 两席统一 ID / owner / severity / closure
→ author 收到唯一批次
```

争议不能靠 author 选择较便宜解释；无法统一时才上提用户裁决。

## 4. 推荐工作流

```text
1. 用户授权 assignment
2. 机械 preflight：
   assignment / branch_slug / needs / PR / gates / trailer 全成立
3. author 自验并发布 frozen candidate T
4. 两 required gater 独立审同一个 T
5. reconciliation barrier：
   合并成唯一 finding ledger，解决严重度/closure 冲突
6. author 一次性处理整批，只 push T2 一次
7. owner gater 做 fix_verification；双方只读各自 delta
8. verdict memo 先开 PR，不逐篇合 main
9. coordinator 批合 memo → author 一次最终 rebase
10. 机械 carry 或一行 re-nail → 静默窗口立即 squash
```

不建议把 required gates 完全串行：独立并行审查仍能降低漏病和从众风险。应增加的是
“独立审查之后、author 修复之前”的 reconciliation barrier。

## 5. 机械化优先级

### 立即可执行，无协议改动

1. finding owner + closure ledger；
2. frozen head + reconciliation barrier；
3. author 每轮单次 push；
4. memo 批合 + main 静默窗口；
5. 第二轮默认 composite，不默认 full。

### 下一刀工具化

1. **`hctl merge`**：从 obligation 推导 PR；禁止猜/手输 PR 号；quorum 未绿硬拒；
   exact-head merge，merge/delete 分阶段校验。
2. **`hctl preflight`**：gater 开工前拒 assignment/branch mismatch、needs 未满足、
   无对应 obligation、trailer 不合规。
3. **结构化 review ledger**：status 展示 owner、open/closed、closure evidence，
   不让状态散在多篇 prose。
4. **`hctl seat init` / `hctl trailer`**：把 bot email/seat 映射从级④手抄迁出；
   model/effort 不可得时 fail closed。
5. **conservative verdict carry**：仅继承
   `APPROVE + COMPLETE`，且必须机械证明 review surface 无新语义；RC 不继承，
   `.hctl`/governance 或受审路径变化不继承。

tree-equivalent carry 的第一刀应谨慎：commit-message-only rewrite 可直接按 tree；
base-only memo/docs 前进更适合比较 PR patch/review surface 与治理面，而不是靠
LLM 判断“看起来无关”。

## 6. 如何判断改进是否有效

为后续 assignment 记录以下过程指标：

- author head 发布次数；
- required gate round 数；
- stale verdict / re-nail 次数；
- reopened finding 数；
- gater severity disagreement 数；
- false-green mutation 被 corpus 杀死的比例；
- merge 前 assignment/branch/trailer preflight 命中数。

目标不是追求“零 REQUEST_CHANGES”，而是：

```text
同一 finding 不重复开启；
每轮 author 只收到一个一致批次；
语义修复只引起一次新 head；
非语义 main 前进不触发 full review；
未绿 PR 在机械层不可能 merge。
```
