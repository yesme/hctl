## 1. 用户需求（原话要点整理）

- 多家 harness（codex/gpt-5.6、claude/fable-5、grok-4.5、opencode/glm-5.2、kimi-k3、agy/gemini-3.6）共享一个 repo，各自建 branch；制定计划须考虑各家能力边界。
- **写串行**：任一时间一个 branch 上只有一个 harness 在写，但可串行做多个写；串行需要 guardrail（active PR 阻塞新 author 工作——用户问这是否带来复杂度，可商量 pros/cons）。**读不限**：多个 review/gate/memo 可并行（memo 各写各家，天然不冲突）。
- 协作限于本机（无 RPC）；但有跨机续跑（故不能用 inode 级手段）。
- **通知/同步**：充分利用本机 repo 与共享 git worktree；git API 有成本与 quota，要挑便宜快的命令；本机有 gh；PR comments 能否不 access API 就 handle；机制必须 mechanical、deterministic、尽量不用 LLM（省 token + 免曲解）。
- **订阅可靠性是已证反复出错点**（PR/comments 交了接收方漏掉，workflow 卡死；title 不 match 等原因）——建议宽进严出：有变化就醒、按提交者过滤、按内容理解而非 title regex。
- **协作以 PR 为基础**：author 开/merge PR，gater 审核，可 re-gate；gater 属性需设计（阻塞等待？explicit yes？只修 P0？超时跳过？可组合如「A 或 B 同意」）。
- **两种驱动模式**：① predefined DAG（author/gate 关系静态完整，边上可反复 regate，但不得动态生成新依赖）；② ad-hoc 指定（动态把两家 link 起来）。
- **角色定位**（用户给定）：GPT-5.6/GLM-5.2 擅逻辑精细、代码、验证，缺全局、爱打 patch → 非愿景非架构模块；Fable-5/Kimi-K3 擅愿景宏观、论文写作，nitting 挂一漏万 → 愿景、问题定义、plan；Grok-4.5 高效、对抗分析特长 → 万金油副手 gate；Gemini-3.6 只能讨论，只能写自家 memo；GPT/Fable/Grok token 够，GLM/Kimi 副手不太够。
- 工作形态：Ghostty 一 harness 一 tab；一个 harness 内可有多个 sub-agent/task（同 LLM）——只能一个 build，可多个 review/plan。
- **过去 phase 的负面案例（心跳老是消失等）必须作为反面案例研究。**
- 用户问：业界有没有类似的好的解决方案？

## 2. Kimi 分析一：业界先例（直接回答用户）

**没有现成的「跨厂商 LLM harness 协作」方案。** 这个设计的本质是 **merge queue + CI DAG + git-native pub/sub，单机尺度，worker 是各家 LLM CLI**。零件在三个领域：

| 领域 | 先例 | 可抄什么 |
|---|---|---|
| 合并队列 | GitHub merge queue / GitLab merge train / Bors-ng / **Zuul**（OpenStack） | 写串行 guardrail 的成熟形态；Zuul 的 `Depends-On` 静态依赖图 = predefined DAG 原型（不允许运行时发明依赖） |
| 代码评审 | **Gerrit**（label / submit requirements） | gater 属性 taxonomy 现成答案：`Code-Review +1/+2`（非阻塞/阻塞）、`Verified`（机器 gate）、submit requirements 任意布尔组合 |
| 工作流引擎 | Temporal / Cadence | 只有一条可借：从事件日志（git 状态）重建全部运行时状态；RPC 重型控制面不符合本机约束 |
| git-native 信令 | Gerrit `refs/changes/*` / git notes / Radicle gossip | 用 git refs 当订阅通道被验证过；比 RPC 便宜、比 inode 可移植 |
| 多 agent 框架 | LangGraph / CrewAI / AutoGen | **不对路**——单进程统一 runtime；本场景是异构 CLI 的 CI/CD，祖先是 Zuul/Gerrit |

## 3. Kimi 分析二：设计中已成立、不必再辩的

1. **机械同步层不用 LLM**——round-01 实证：token 省、歧义零。
2. **宽进严出的订阅**——具体形态：`for-each-ref` 本地 2s 轮询醒 → `gh` 带 ETag 条件请求（304 = 零 quota）→ committer 白名单过滤 → **body 结构化事件块**（ROUND-GATE-EVENT v1 式 fenced block）分类；**title 永不作判据**。
3. **PR-based + 静态 DAG / ad-hoc 双模**——批量工程走 DAG，单点配对走 ad-hoc，共用同一套 gate 语义。
4. **AGY 只讨论不落盘、Grok 万能副手**——与实战证据一致。

## 4. Kimi 分析三：四个待定点的 pros/cons

### 4.1 写锁粒度（用户主动问）

| 方案 | pros | cons |
|---|---|---|
| **branch 级 active-PR 锁**（现案） | 简单、确定、无判读成本 | head-of-line blocking：一个 PR 卡 gate，同 harness 后续 author 全堵 |
| path 级锁 | 并行度高 | 需声明文件集 + 冲突判定，复杂度翻倍 |

**建议：** v1 用 branch 锁 + gate timeout + 配对 gate fallback（已有），把等待复杂度转移给 timeout/failover 消化；出现真实 head-of-line 阻塞案例后再升级 path 锁。

### 4.2 Gater 属性闭集（抄 Gerrit 五维，不新造）

**quorum（n-of-m）× blocking（hard/soft）× timeout action（escalate/skip/degrade）× scope（full/P0-only）× independence（非作者/无污染会话）**；所有组合在 DAG 静态声明，运行时不得发明新替补（round-01 fallback 表已是雏形）。

### 4.3 通知/同步四层选型

| 层 | 选型 | 理由 |
|---|---|---|
| 醒 | `git for-each-ref` 本地 2s 轮询 | 零成本、机械、跨机 fetch 即见 |
| 拉 | `gh api` + ETag（304 零 quota） | GIT-PROTOCOL §8 已验证 |
| 滤 | committer 白名单 + body 结构化事件块 | 宽进严出；title 永不作判据 |
| 死信 | 订阅端记 last-seen cursor，超时未消费显式上报 | 治「PR 交了接收方漏掉」的现病 |

### 4.4 跨机续跑

只承认 git 可达状态（refs、merged PR、结构化评论）为事实源；本机临时态（pid、inode、mtime）一律不作恢复依据（round-01 §5 已是此形）。

## 6. 对「script/policy/guideline 满天飞」的清理原则

新架构必须**替代而不是叠加**：同步层一个目录（`scripts/round/` 级）、协议一个文件（ROUND-PROTOCOL 级）、DAG 一个目录（rounds/）、事件一种格式（gate event block）。不进这四样的机制默认删除——这是 spec 树整洁原则在协作层的应用。

## 7. 落地顺序建议

1. 把现有 `scripts/round/` 工具链抽象成项目无关的 repo 模板（已覆盖 merge queue + DAG + 心跳 + 配对 gate）；
2. gater 五维属性写成 DAG 机器可读 schema（fallback 表是雏形）；
3. 「结构化事件块 + committer 过滤 + ETag 拉取 + last-seen cursor」固化成订阅端参考实现；
4. 跨机恢复写成一页 SOP（fetch → 推导 merged PR + quorum 事件 → 续跑）。
