## 一、用户需求与约束（原话要点）

### 能力边界（排兵布阵依据）
- **GPT-5.6-sol / Fable-5 > GLM-5.2 / Kimi-K3**：擅长逻辑分析、精细写作、代码、严谨验证；**缺全局视角、drill down 细节、prefer patch 而非架构合并**。适合 spec 非愿景模块（artifact/primitive/域定义/函数行为）。
- **Fable-5 / Kimi-K3**：擅长愿景、宏观、论文、问题定义、plan 规划；**nit-fix 挂一漏万**。适合愿景文体、问题定义、plan。
- **Grok-4.5**：效率高、对抗分析特长；主业外作万金油副手 gate。
- **Gemini-3.6-flash（AGY）**：只讨论，**不落盘除自己 memo 外的任何文件**。
- token：GPT/Fable/Grok 够；GLM/Kimi 不够（副手级，有界审阅）。

### 协作约束
1. 共享 repo，各自 branch。
2. **一个 branch 任一时间只有一个 harness 写**（串行写），可串行多写任务；**读（review/gate/memo）并行不受限**（多 context 各写独立 memo，本质不冲突）。
3. guardrail：active PR 时新 author 等待（用户问 pros/cons）。
4. 范围本机，但有**跨机续执行**（当机跑阶段一，另一机跑阶段二）。
5. 通知/同步：充分用本机 repo / 共享 git worktree；跨机不能用太 native（inode）手段；git API 有 quota 谨慎挑"便宜快"命令；本机装 gh 可操作 PR（PR comments 能否不 access API handle）；**mechanical / deterministic，尽量不用 LLM**（省 token + 避免曲解）。
6. **可靠订阅是反复出错点**‼️（交了 PR/comments 但接收方漏接 → workflow 卡死，原因多：title 不 match 等）。建议**宽进严出**（有变化就醒 / 按提交者过滤 / 内容理解非 title regex）。
7. 协作以 **PR** 为基础：author + gaters。gater 属性：阻塞等待 / 需 explicit yes / 只修 P0 / 长时间无反应跳过——可合并、可组合（"A 或 B 同意就行"）。
8. 驱动：用户手动在各 harness prompt 输入。两模式：① **predefined DAG workflow**（author/gate 关系完整定义，可 regate，执行中不动态生新 dependency）；② **ad-hoc 指定**（"这个交 codex gate"动态 link）。
9. Ghostty 多 tab（每 harness 一 tab），harness 内可多 sub-agent/task（同 LLM）：**一个 build，多 review/plan**。
10. 负面案例（心跳老是消失）作反面研究。
11. 业界有没有类似方案？

## 二、GLM 整体判断：Prow-lite，本机，人在环，LLM 在边缘

本质是 **GitHub PR 协作流程（author/reviewer/CI）的本机化 + LLM 边缘化 + git-native 信号化**。**不需要发明新机制**——PR/branch/ref/lock/quorum/fallback 都是成熟的。要做的是**精选成熟机制 + 解决三个本机/LLM 特有的真问题**（见 §四）。

## 三、业界先例（用户明确问）

| 系统 | 对应什么 | 与用户差异 |
|---|---|---|
| **Prow**（K8s/CNCF CI）| tide（gate quorum→auto-merge）+ hook（事件订阅）+ plank（job）——**最接近** | 服务端 webhook；用户本机无服务端 |
| **Zuul**（OpenStack）| gate pipeline + cross-project dep | 服务端 |
| **Gerrit**| submit requirement（prolog 规则）= declarative gate | 中心化 server |
| **GitHub Actions + branch protection**| required reviews / status checks = declarative gate | 服务端 |
| **Temporal/Cadence**| durable workflow + activity = **跨机续执行** | 程序化，非人驱动 |
| **Bazel/Buck**| DAG + hermeticity（author unit 类比）| build system，非 review |
| **ArgoCD/Flux（GitOps）**| git as source of truth | 用户已 git-native |
| LLM multi-agent（AutoGen/CrewAI/LangGraph）| 多 agent | **程序化 agent，非人驱动 TUI** |

**结论**：业界**无完全对应**——用户组合（人驱动 TUI + 本机 + LLM 边缘 + git-native）是**原创综合**。Prow 最近但服务端 + 非 LLM。用户是「Prow 的 gate 模型 + GitOps 的 git-native + 人在环 + LLM 只在节点内部」。

## 四、需求 → 六组件映射（现成机制）

| 需求 | 机制 | 现成？ |
|---|---|---|
| 共享 repo 各 branch | git worktree-per-harness | ✓（已有）|
| 一 branch 一时间一写 | git 本身（branch checkout 独占 worktree）| ✓ 天然 |
| 并行读（review/memo）| worktree 内多 context，memo 各自文件 | ✓ 天然 |
| 跨机续执行 | git-native ref + state in commits（push/ls-remote）| ✓ GIT-PROTOCOL §2 已有 |
| PR comments 不 access API | **做不到**——GitHub 不 push comments 到本地 | ✗ 只能 gh API + **ETag（304 不计 quota）** |
| mechanical / 少 LLM | 协作总线 ref/lock/quorum（deterministic）| ✓ |

**硬伤**：「PR comments 不 access API」——GitHub 不把 comments push 到本地 ref，只能 API。最优解已在 GIT-PROTOCOL §8：**ETag 条件轮询**（`If-None-Match`，304 不计 quota，30s）。这是"便宜又快"的上限，除非上 webhook（要服务端，违背本机约束）。

## 五、三真难点（负面案例集中地）

### 1. LLM-free 可靠通知——基本解决（§8 宽进严出 + ETag）
唯一未决：**PR comment 语义判定**（这条评论是 PASS 还是 REQUEST_CHANGES？）。mechanical 做不到语义——但已有**结构化 gate 评论格式**（gate.py `GATE-RESULT | reviewer=X | result=PASS`），机械 parse 这一行即可，不读全文。**LLM 不进总线**。

### 2. 心跳活性（round-01 三次 interrupt 根因）——未解决
sidecar.sh:64-65 **故意在 session 不活跃时不写**（等 user 时 session 无 mtime → 不写 → watchdog 3m 判死）。对话 agent 等 user 必然 session 不活跃 → 必判死。

**解法方向**：heartbeat 不能靠 session mtime（那是"在干活"信号，非"活着"信号）。要么 mechanical heartbeat（worker 进程内固定间隔 tick，与 session 无关）；要么 generation CAS + 可观察停信号（codex P0-1：fire 撤 active ref → wait_tick 写后复核自停）——那是"何时停"非"等 user 保活"。对话 agent 的"等 user 间隙"本质需**后台 heartbeat 进程**（nohup tick loop），与对话响应解耦。

### 3. declarative gate 配置落点——待定
DAG file（predefined round）已解决。**ad-hoc 指派**（"codex gate 这个 PR"）落哪？候选：PR body frontmatter（`gate: [codex]`，人可读 + 机械 parse）/ git note（`refs/notes/gate-config`，不污染 body）/ PR label（`gate-codex`，GitHub 原生 + API）。**建议 PR body frontmatter**（人驱动时顺手写，机械 grep）。

## 六、用户问的 pros/cons

### 「active PR 时新 author 等待」——建议不要隐式等待，用显式 lock
- pros：避免一 branch 两 author 冲突。
- cons：隐式等待引死锁（A 等 B PR，B 等 A review）+ 等待管理复杂（timeout？换人？）。
- **建议**：branch 独占已由 **git worktree 天然保证**（一 branch 一 worktree，物理无法两 author 同时写）。若要多 author 串行写同 branch，用 **explicit lock ref**（`refs/lock/<branch>`，acquire/release），新 author 检查 lock——有就**报告用户裁决**（等？换 branch？），不隐式等待。隐式等待是复杂度来源，显式 + 人工裁决更稳。

### gater 属性设计——拆三个正交维度 + 组合
| 维度 | 取值 | 含义 |
|---|---|---|
| **blocking** | required / advisory | author 能否在它未 PASS 时 merge |
| **strictness** | explicit-yes / no-P0 / any-response | PASS 判据 |
| **liveness policy** | wait / timeout-skip / fallback-chain | 无响应时 |

组合 = `blocking × strictness × liveness`。用户的"A 或 B 同意"= **quorum**（required gaters 里 N 个 PASS）+ **fallback chain**（A 失效→B→C）。正是 ROUND-PROTOCOL §2 配对 gate 的 `author/primary/deputy/reserve/floor/activation`——已是 declarative 组合，**抽出来泛化即可**。

## 七、可靠订阅（用户最大痛点）——已在你 GIT-PROTOCOL §8

已踩坑（事故 #139：title regex 漏接）。解法已写：
- **宽进**：`git ls-remote refs/pull/*/head`（SHA 变 = 新 PR/head 动，零 API quota）+ `gh api comments ETag`（304 不计 quota）——任何结构变化唤醒。
- **严出**：唤醒后**读 PR 本体**（files/body/labels/assignees）判断相关性，**不用 title regex**。

不需新设计——§8 已是最佳实践，抽进方法论即可。
