# Harness 协作架构：从脚本集合收束为协作内核

> 日期：2026-07-26
>
> 作者：Codex / GPT-5.6 Sol / ultra

> 讨论基线：`6f945fd7bb52615a61c73f3ad3e43c560142a64f`

## 1. 背景与问题

近期 round 实践暴露了一个更一般的问题：当前项目中的协作能力逐渐分散到 protocol、policy、guideline、harness 启动文件和 shell script 中。同一规则常有多个文本来源和多个实现来源，修复一个竞态或遗漏后，需要同时修改多处；任何一处漏改，都会产生新的漂移。

因此，这次讨论的目标不是继续修补现有 round，而是设计一套独立于 CoAgNET、可单独部署的 harness 协作方法与工具。它面对的工作环境是：

- 多家 harness 共享同一仓库，各自有稳定的工作目录和分支空间。
- 任一 harness 同时最多执行一个会修改正式内容的 author 工作。
- review、gate、analysis 可以并行。
- 工作通常由人在多个 Ghostty tab 中直接下达 prompt。
- 同一 harness 可以运行多个同模型 sub-agent，但只有一个可以进入 author 临界区。
- 协作主要发生在一台机器上，但任务可能在另一台机器继续。
- GitHub PR 是正式交付和审核边界。
- GitHub API 调用有成本，通知机制必须便宜、可靠、可恢复。
- 任务调度和结果识别应当是机械、确定性的，不能依赖 LLM 猜测标题或自然语言。

可用 harness 的当前能力分布属于项目配置，而不是通用协议本身：

- Codex / GPT-5.6 Sol：精细逻辑、字段级定义、代码、严格验证。
- OpenCode / GLM-5.2：与 Codex 相近，但 token 较紧。
- Claude Code / Fable-5：愿景、架构、问题定义、长文主线。
- Kimi Code / Kimi-K3：与 Fable 相近，但 token 较紧。
- Grok Build / Grok-4.5：高效率、对抗分析、通用 gate。
- Antigravity / Gemini-3.6 Flash：讨论和自有 memo，不修改 canonical 文件。

## 2. 根因判断

当前混乱的根因不是“规则还不够多”，而是**同一行为存在多个真相来源**：

1. 文档规定应当怎样做。
2. harness 启动文件再次转述。
3. shell script 实现其中一部分。
4. PR 标题和评论格式暗含另一部分路由规则。
5. 人工 prompt 又补充例外和临时裁定。

这种结构会自然地产生两个结果：

- 文本与执行漂移。脚本已经变化，policy 仍描述旧行为；或 policy 已经收紧，脚本没有阻止违规操作。
- 修复叠加。每次事故都新增脚本、字段、心跳或 guard，而没有消除旧状态源。

新的系统应当收束为：

> 一份规范、一个机器配置、一个执行程序、一份可丢弃并重建的本地状态。

暂称 **Harness Collaboration Kernel**，命令行程序暂称 `hctl`。名称尚未裁定。

## 3. 两个需要纠正的并发假设

### 3.1 不同 memo 文件不等于可以在同一 branch 并发提交

不同 context 写不同 memo，只避免了文件内容冲突，没有避免 Git 状态冲突。同一 worktree 或 branch 仍然共享：

- Git index；
- branch HEAD；
- 当前 PR 的 head SHA；
- gate 绑定的受审版本。

具体失败场景：

1. Codex 正在 author 一个 PR，Grok 和 GLM 同时完成 review。
2. 两个 reviewer 分别向同一 author branch 提交自己的 memo。
3. 即使文件完全不同，PR head 仍然发生变化。
4. 所有绑定旧 head SHA 的 gate 都应失效。
5. 如果系统没有失效它们，就会把未受审的 memo commit 一并 merge；如果系统正确失效，又会造成无意义的重复 gate。

因此必须区分“并行分析”和“并行发布”：

| 工作类型 | 是否修改正式分支 | 并发方式 |
|---|---:|---|
| Author | 是 | 每个 harness 最多一个 |
| Gate / Review | 否；正式结果写 PR 评论 | 可并行 |
| Analysis / Plan | 否 | 可并行 |
| Memo 草稿 | 写独立 spool | 可并行 |
| Memo 发布 | 写 notes lane 或 main | 串行 |

如果项目仍要求把每份 review 报告归档进 Git，应先让各 context 写入独立 spool，再由一个 record publisher 串行提交。更进一步，可以把临时 review 留在 PR，只有已经收敛的设计决定和 retrospective 才进入主库。

### 3.2 心跳不是协作义务的正确载体

round 全程心跳混淆了三种状态：

- TUI 或进程是否仍在运行；
- worker 是否仍承担某项义务；
- 工作是否取得进展。

过去的失败说明，心跳一旦承担正确性职责，就会产生脆弱的全局耦合：

1. 一家 worker 短暂失联或工具调用阻塞。
2. 系统把它误判为死亡。
3. 无关节点被暂停或中断。
4. worker 恢复后，系统无法仅凭心跳判断旧结果是否仍然有效。

新的系统不应要求 worker 在整个 round 内维持心跳。任务、PR、gate 和 deadline 是持久事实；进程存活只是运行时信息。超过 deadline 的任务进入 `stalled` 或 `timed_out`，但不得使无关节点失效。

如果需要监控，应监控唯一的本地 watcher，而不是要求每个 LLM 定期证明自己还活着。

## 4. 总体架构

### 4.1 持久事实层

跨机器可恢复的正式事实包括：

- 已封存的 WorkOrder 或 workflow；
- 远端 Git branch 和 commit；
- GitHub PR；
- PR 的精确 head SHA；
- 结构化 gate event；
- PR merged、closed、draft 等状态。

本地 SQLite、JSON、锁文件、ETag、轮询游标都只是：

- 本地缓存；
- 临时 author lease；
- 唤醒提示；
- 从正式事实计算出的状态投影。

这些内容必须可以删除。换机后运行 `hctl reconcile`，应能从远端事实重建。

### 4.2 确定性协作内核

`hctl` 负责：

- 校验项目配置和 WorkOrder；
- 管理每个 harness 的唯一 author slot；
- 从 PR、head 和 gate event 推导任务状态；
- 评估 gate quorum；
- 发现 stale gate；
- 管理 deadline、fallback 和 stalled 状态；
- 执行 handoff、recover 和 merge 前检查；
- 产生结构化评论；
- 输出给人和 harness 阅读的简短状态。

不应由 `hctl` 负责：

- 判断文档设计是否正确；
- 从自然语言猜测 reviewer 的结论；
- 自动选择“最聪明”的模型；
- 替代 GitHub、Git 或现有 merge protection；
- 证明各 harness 在对抗环境中的密码学身份。

### 4.3 Harness 适配层

通用内核只识别 capability、写权限、token budget 和并发限制，不硬编码模型排名。项目配置可以声明：

```yaml
harnesses:
  codex:
    capabilities: [wire, state-machine, implementation, interop-review]
    canonical_write: true
    author_concurrency: 1
  claude:
    capabilities: [vision, architecture, planning, narrative]
    canonical_write: true
    author_concurrency: 1
  grok:
    capabilities: [adversarial-review, general-gate]
    canonical_write: true
    author_concurrency: 1
  agy:
    capabilities: [discussion, review]
    canonical_write: false
    memo_scope: own
```

Planner 仍由人或上层流程决定；`hctl` 只验证分配是否违反能力和权限约束。

## 5. WorkOrder：统一预定义 DAG 与 ad-hoc

两种协作模式不应发展成两套执行引擎。它们都编译为同一种不可变 WorkOrder。

### 5.1 预定义模式

- 完整 DAG 在执行前声明。
- 以内容 hash 或版本号封存。
- 执行期间不得修改已有节点和 dependency。
- 如果产生新需求，创建引用原结果的新 WorkOrder。

### 5.2 Ad-hoc 模式

“让 Grok gate Codex 的 PR”不是直接篡改一个正在运行的 DAG，而是创建一个小型 WorkOrder：

- 输入：目标 PR 和 head SHA；
- worker：Grok；
- 类型：gate；
- gate policy：required、advisory 或 observe；
- 输出：结构化 GateEvent。

这样既允许动态协作，也保留确定性、可审计性和可恢复性。

## 6. 状态应当由事实推导

不要再维护一个与 GitHub 平行、可以任意改写的“round 状态板”。WorkOrder 是不可变输入，PR 和 gate event 是事实，状态是计算结果。

建议投影状态：

```text
queued
  -> authoring
  -> pr_open
  -> gating
  -> changes_requested
  -> gating
  -> merge_ready
  -> merged
```

旁路状态：

```text
stalled
cancelled
superseded
```

`reconcile` 每次都重新检查事实，不依赖“上一次脚本运行到哪一步”。这是一种 level-triggered 模型：即使漏掉一条通知，下一次完整计算仍会得到正确状态。

## 7. 分支与单写者模型

### 7.1 推荐使用 harness namespace 下的 task branch

不建议在独立方法中继续把每个 harness 固定为一个长期远端 branch，例如 `codex/main-mac`。长期分支会带来：

- squash merge 后需要反复复位；
- 一个 memo commit 可能混入另一个 PR；
- 跨机器接续需要理解机器后缀；
- 多个任务共享 branch 身份，状态边界不清楚。

建议改为：

```text
work/codex/<task-id>
work/claude/<task-id>
work/grok/<task-id>
```

本地仍可保留 `abacistopia-codex` 这类 harness 专属 worktree，只是 worktree 切换到当前 task branch。

机器名属于本地执行环境，不应进入远端任务身份。这样 Mac 开始、Ubuntu 继续时，接续的是同一个 task branch。

现有项目可以先通过 adapter 兼容长期 branch，不要求一次迁移完成。

### 7.2 Author slot

`hctl begin` 为 `(repository, harness)` 获取一个唯一 author slot。它是逻辑任务锁，不是进程锁：

- 当前 author task 未 merge、cancel 或 handoff 时，新 author task 只能 queued。
- review、analysis 不占 author slot。
- 建议尽早创建 draft PR，使远端 PR 成为跨机器可见的持久任务记录。
- 本地 bootstrap 阶段由 SQLite 唯一约束防止同机竞态。

等待本身不会带来很大复杂度，前提是等待由内核队列承担，而不是让 LLM 不断轮询和发送心跳。

### 7.3 跨机器接续

V1 应明确假设：

> 同一 harness 可以跨机器串行接续，但不支持在两台机器同时 author。

换机前：

1. `hctl handoff` 检查 worktree；
2. commit 或生成明确 checkpoint；
3. push task branch；
4. 创建或更新 draft PR；
5. 写入 handoff event。

另一台机器：

1. fetch；
2. `hctl reconcile`；
3. checkout 同一 task branch；
4. `hctl resume`。

只有未来确实需要跨机器同时抢占同一 author slot 时，才增加远端 CAS lease。现在不应为尚不存在的并发需求引入分布式锁。

## 8. Gate 模型

用户提出的 gate 属性可以收束为四个正交维度，而不是一组相互覆盖的布尔字段。

### 8.1 Mode

```text
required
advisory
observe
```

- `required`：必须拿到当前 head 上的显式 PASS。
- `advisory`：在反馈窗口内等待；若没有响应，可以按预定规则继续；若已收到阻塞 finding，则必须闭合。
- `observe`：只记录结果，不影响 merge。

“是否阻塞等待”和“是否必须 explicit yes”不应完全分开。required 的定义就是阻塞并要求显式 PASS；advisory 才允许无响应后继续。

### 8.2 Quorum

不需要通用脚本语言。有限的析取范式已足够覆盖：

```text
Codex
Codex AND Grok
Codex OR Grok
Claude AND (Codex OR GLM)
2 of [Codex, Grok, GLM]
```

### 8.3 Blocking threshold

```text
P0
P1
all
```

“只要求修 P0”意味着 P1/P2 仍作为反馈保留，但不阻塞 gate。GateEvent 应显式给出 verdict 和最高 finding severity，不能要求内核从自然语言中推导。

### 8.4 Timeout

```text
fail
fallback
proceed
```

- required 默认 `fail`。
- required 只有在 WorkOrder 预先声明替代 reviewer 时才能 `fallback`。
- advisory 可以 `proceed`。
- required 不得因为“等得太久”而静默跳过。

### 8.5 Freshness

每个 GateEvent 必须绑定：

- WorkOrder ID；
- PR number；
- gate ID；
- reviewer harness；
- exact head SHA；
- result；
- event version。

PR head 变化后，旧 head 上的 PASS 自动变为 stale。不得依靠 reviewer 自己记得重新 gate。

## 9. 结构化评论与宽进严出

过去依靠 PR title、分支命名或自然语言 regex 路由，已经多次漏掉有效结果。新的通知应把“唤醒”和“满足条件”分开。

最终 gate verdict 使用普通 PR conversation comment，并带隐藏的机器标记：

```html
<!-- hcollab:v1 {"work_id":"W42","gate_id":"adversarial","pr":868,"head":"abc123","reviewer":"grok","result":"PASS"} -->
```

其后是供人阅读的 review 正文。

规则：

- 任何 comment、review comment、head 变化、PR 状态变化都可以唤醒 reconciler。
- 只有 marker 中的 work、PR、head、reviewer、gate 和 result 全部匹配，才满足 gate。
- 无 marker 的评论会被展示为 `unclassified_feedback`，不能自动满足 gate。
- Inline review comment 是 finding，不是最终 verdict。
- 同一 reviewer 在同一 head 上可追加新 event；按 GitHub event 顺序取最后一个有效 event。
- 旧 head 上的任何 event 都保留作历史，但不参与当前 gate。

这里的“根据内容理解”应当解释为读取结构化语义，而不是调用 LLM 猜测自然语言。系统可以宽泛地被任何变化唤醒，但输出必须经过严格字段校验。

当前所有 harness 通常共用一个 GitHub 人类账号，因此 GitHub comment author 不能证明是哪家 harness。V1 属于受信本机 profile，可以接受 marker 中声明的 harness 身份。若以后需要对抗性身份，再使用独立 GitHub App/bot 身份或标准签名机制；现在不应先发明一套签名协议。

## 10. 通知与 API 成本

### 10.1 本地 Git 的能力边界

本地 Git 无法读取 GitHub PR comments：

- `git fetch` 和 `git ls-remote` 只能读取 Git refs 和对象；
- PR comment、review、状态检查属于 GitHub 数据库；
- `gh pr view`、`gh api` 仍然是 GitHub API 调用。

若坚持完全不调用 API，只有两个替代方向：

1. 把 gate verdict 重复写入 Git refs 或 commit；
2. 部署 webhook receiver。

第一种会制造第二套事实和新的写竞态；第二种需要常驻、可访问的服务。当前规模下都不如节制地使用 API。

### 10.2 推荐的本地 watcher

每个 repository、每台活跃机器只运行一个 watcher：

- 只监控 WorkOrder 中已知的 active PR；
- API 请求串行执行；
- 保存 `ETag` 和 `Last-Modified`；
- 使用带认证的 conditional GET；
- `304 Not Modified` 时不解析正文；
- 仅对发生变化的 PR 获取 canonical comment stream；
- 遵守 `X-Poll-Interval`、`Retry-After` 和 rate-limit headers；
- idle 时指数退避；
- 定期运行完整 reconcile，修复漏事件。

GitHub 官方建议优先使用 webhook；同时明确，正确认证的 conditional GET 若返回 `304`，不计入 primary rate limit：

- <https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api>

本机协作没有稳定公网 receiver，又只有少量 active PR，因此“一个集中 watcher + 条件轮询 + 定期全量 reconcile”比每个 TUI 单独调用 `gh` 更符合当前约束。Webhook 可作为未来高规模 profile，而不是 V1 前置条件。

### 10.3 不再使用 round-wide heartbeat

Watcher 只监控持久事实变化。它不试图证明某个 LLM tab 是否活着。

- author 长时间没有结果：task 超过 deadline，标为 stalled。
- required gater 长时间没有回应：gate timeout，按 fail 或预定 fallback 处理。
- advisory gater 没有回应：反馈窗口关闭后 proceed。
- watcher 重启：从 WorkOrder 和 GitHub 重建，不丢状态。
- 一家 worker 消失：不影响其他独立节点。

## 11. Merge 与执行强度

### 11.1 协作 profile

V1 可由 `hctl merge` 在本地检查：

- PR head 与 gate 绑定 SHA 一致；
- quorum 已满足；
- 没有当前 threshold 下的 blocker；
- branch 属于声明的 harness/task；
- base 和 freshness 策略满足；
- merge method 为项目声明的 squash、rebase 或 merge。

这能防止正常操作误合并，但无法阻止有权限的人绕过 `hctl`，直接在网页或 `gh pr merge` 合并。

### 11.2 强制 profile

需要技术强制时，可以复用 GitHub 能力：

- GitHub Action 或 App 运行同一 gate evaluator；
- 输出 `harness-collab/gate` status check；
- ruleset 将它设为 required check；
- 必要时限定 status check 必须来自指定 GitHub App；
- 多 PR 同时进入 main 时使用 GitHub merge queue。

权威参考：

- Required status checks 与可信 App 来源：

  <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets>

- Merge queue：

  <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue>

不应在本地脚本中重新实现 merge queue 或 speculative merge。

## 12. 业界参照

这个问题并不新。特殊之处只是 worker 是由人手动 prompt 的 LLM harness；其控制问题与代码审核、CI gating 和作业队列高度相似。

### 12.1 Gerrit

可借鉴：

- 一个 change 有多个 patchset；
- approval 绑定具体受审版本；
- submit requirement 使用声明式表达式；
- 可以要求非 uploader 的审核；
- requirement 可测试、可计算。

参考：

- <https://gerrit-review.googlesource.com/Documentation/config-submit-requirements.html>

对应本提案：

- PR head SHA 相当于 patchset；
- GateEvent 绑定 exact head；
- quorum 相当于收窄后的 submit requirement。

### 12.2 Zuul

Zuul 已明确区分：

- `independent`：互不影响、可并行的 check；
- `dependent`：面向 merge gate 的依赖队列；
- `serial`：共享队列中一次只处理一个工作。

参考：

- <https://zuul-ci.org/docs/zuul/latest/config/pipeline.html>
- <https://zuul-ci.org/docs/zuul/latest/gating.html>

这与本场景的 review、gate、author slot 很接近。但不建议直接部署 Zuul：

- Zuul 是常驻中心化服务；
- 面向自动触发的 CI jobs；
- 运维和配置体量远大于六家本地、人工 prompt 的 harness；
- 会把一个方法论问题变成一套服务运维问题。

应借鉴它的队列和 pipeline 模型，不照搬它的部署形态。

### 12.3 GitHub

应直接复用：

- PR 作为变更和讨论边界；
- status check 与 ruleset 作为强制门；
- merge queue 处理 base branch 竞争；
- REST conditional request 降低轮询成本。

这部分不需要另造协议。

## 13. 独立项目的最小形态

协作内核应建立为独立 Git repository，而不是当前项目下的一个新目录。原因是：

- 它服务于多个项目，生命周期不从属于 CoAgNET。
- 它需要独立的版本、发布、兼容性与回归测试。
- 它必须能在不读取 CoAgNET memory、discussion 和 review policy 的情况下使用。
- CoAgNET 应是首个 consumer 和事故样本来源，而不是通用协议的所有者。
- 若把实现留在当前仓库，项目特例会继续进入通用内核，无法真正清理责任边界。

建议 repository 暂名 `harness-collab`，CLI 暂名 `hctl`。不使用 Git submodule；consumer 通过发行版本或精确 commit pin 声明所使用的内核版本。

Standalone repository：

```text
METHOD.md
schema/
  project.schema.json
  work-order.schema.json
  gate-event.schema.json
hctl
examples/
optional/
  github-action/
```

其中：

- `METHOD.md` 是唯一规范文本，只描述不变量、事实模型和失败行为。
- JSON Schema 是机器配置的唯一结构定义。
- CLI help 从命令和 schema 生成，不另写一套操作手册。
- examples 只示范，不产生新的规范义务。
- incident corpus 保存反例和回归测试，不混入主规范。

Consumer repository：

```text
.harness/
  project.yaml
  workflows/
COLLABORATION.md
```

其中：

- `project.yaml` 声明 harness、capability、branch/path 规则和默认 gate profile；
- `workflows/` 只保存需要版本化的预定义 WorkOrder；
- `COLLABORATION.md` 只说明入口、版本和项目特例，不复制 METHOD。
- CoAgNET 当前的 memory 保留问题来源和决策过程，但不成为通用内核的运行依赖。

Local untracked state：

```text
.git/harness-collab/state.db
```

或：

```text
~/.local/state/harness-collab/<repo-id>/state.db
```

它保存 ETag、lease、cursor 和 derived projection，可以随时删除重建。

## 14. 反面案例应成为验收测试

过去 phase 中的事故不是背景故事，而应构成实现前必须通过的测试 corpus。

### 14.1 通知与路由

- PR title 不匹配：comment 仍会唤醒，按 marker 正确路由。
- comment 到达但 head 未改变：仍会唤醒。
- watcher 在 comment 到达时停止：重启后的 full reconcile 可以发现。
- 无结构评论：被显示为待分类，但不能误判为 PASS。
- 共享 GitHub 账号：不依赖 GitHub review author 区分 harness。

### 14.2 版本与 gate

- reviewer 对 head A 给 PASS，author 推送 head B：A 的 PASS 必须 stale。
- 同一 reviewer 先 REQUEST_CHANGES 后 PASS：当前 head 上最后一个有效 event 生效。
- gate comment 指向错误 PR 或 work ID：不能满足 quorum。
- A-or-B quorum：任一家有效 PASS 即可。
- required timeout：默认 fail-closed。
- advisory timeout：没有阻塞反馈时可继续。

### 14.3 并发与恢复

- 同一 harness 两个 author 同时 begin：只能一个获得 slot。
- author PR 打开期间发布 memo：不得改变 author PR head。
- writer 崩溃：任务保持可恢复，不因没有心跳自动释放给第二 writer。
- watcher 崩溃：不改变任务事实。
- Mac handoff 到 Ubuntu：删除本地状态后仍能从 branch、PR 和 WorkOrder 恢复。
- 一家 gater 消失：其他独立节点继续运行。

### 14.4 Merge

- 当前 head 未通过 gate：`hctl merge` 拒绝。
- base 前进：按 freshness policy 重新检查。
- 两个已通过 PR 同时等待 main：交给 GitHub merge queue，而不是本地抢锁。
- 未启用强制 profile 时绕过 `hctl`：明确记录这是 V1 的信任边界。
- 启用强制 profile 后：required status check 阻止绕过。

## 15. 建议的实施顺序

### Phase 0：裁定方法，不写执行代码

- 收集并分类当前所有 script、policy、guideline。
- 标记每条规则的事实来源、执行者和失败行为。
- 把历史事故整理成测试 corpus。
- 对 task branch、memo lane 和 enforcement profile 作出决定。

### Phase 1：最小内核

只实现：

- project/work-order/gate-event schema；
- `hctl status`；
- `hctl reconcile`；
- `hctl begin`；
- 单 author slot；
- gate parser/evaluator；
- `hctl gate`；
- `hctl merge --check`；
- `hctl handoff/resume/doctor`。

不实现自动模型选择、RPC、远端分布式锁或 webhook 服务。

### Phase 2：通知

- 一个 repository watcher；
- conditional REST polling；
- local state cache；
- deadline 和 stalled 提示；
- full reconciliation。

### Phase 3：可选强制

- GitHub Action/App；
- required status check；
- ruleset；
- merge queue。

### Phase 4：迁移与删除

- 选一轮真实协作，让旧机制与新内核并行运行；
- 对比两者输出；
- 通过全部历史反例测试；
- 建立旧文件到新能力的迁移表；
- 删除被替代的 scripts 和重复 policy；
- 消费仓库只保留一个入口文档和项目配置。

不要先删除旧机制再补功能，也不要让新旧机制长期同时成为有效真相。

## 16. 当前建议与待裁决事项

### 16.1 当前建议

1. 建立独立的协作内核，而不是继续扩写现有 ROUND-PROTOCOL。
2. 通用规范只定义事实、状态、不变量和失败行为；项目能力分配留在配置。
3. 使用 task branch，而不是长期复用 machine-suffixed harness branch。
4. 每个 harness 一个 author slot；review 和 analysis 可并行。
5. Gate 结果进入结构化 PR comment，review memo 不修改受审 branch。
6. 取消 round-wide worker heartbeat，以 deadline、stalled 和 reconcile 取代。
7. 预定义 DAG 与 ad-hoc 统一为不可变 WorkOrder。
8. GitHub 是跨机器事实源，本地数据库只是可重建缓存。
9. V1 使用一个集中 watcher 和 conditional polling；webhook 留作可选扩展。
10. 强制 merge protection 复用 GitHub status check、ruleset 和 merge queue。

### 16.2 需要进一步讨论的三项选择

**分支策略**

- 推荐：`work/<harness>/<task-id>`。
- 兼容方案：继续长期 harness branch，但仍需要独立 author slot 和严格 PR head 隔离。

**Memo 策略**

- 推荐：PR 保存过程性 review；main 只保存收敛后的决定和 retrospective。
- 兼容方案：独立 spool + 串行 notes publisher，把每份报告归档进 Git。

**强制程度**

- 推荐先运行协作 profile，由 `hctl merge` 做本地门禁。
- 稳定后再启用 GitHub required check，避免在方法尚未收敛时先建设 App 和 ruleset。

## 17. 结论

这个系统不需要一个新的分布式调度平台。它需要的是一个足够小、可重放的协作控制面：

- Git 和 GitHub 保存事实；
- 不可变 WorkOrder 描述计划；
- exact-head GateEvent 描述审核结果；
- 单 author slot 约束写入；
- reconciler 从事实推导状态；
- 本地 watcher 负责便宜地唤醒；
- GitHub 原生能力负责最终强制。

最重要的收束不是“把现有脚本重写成一个更大的脚本”，而是消除重复状态源。只有规范、配置和程序之间各司其职，当前的 script、policy、guideline 才不会在下一轮事故后重新增长。
