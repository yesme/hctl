## 0. 总判

**方向通过，不能按现有文字直接开写 P1。**

三层承载、level-triggered derive、任务分支、memo lane、每席事件链、required gate
fail-closed、无常驻服务，这组骨架互相相容；其中任务分支与纯推导尤其值得保留。当前需要在
P0 先补齐六个阻断项：

1. `EDGE` 现在同时指“图的边”和“可认领工作项”，尚无可机械生成的 obligation identity；
2. “六类事件一律钉 head”不成立，EDGE/CLAIM/NOTE/CANCEL 可能发生在 head 出现之前；
3. CLAIM 是**两阶段 CAS**，不是一个跨本地与远端的原子事务；remote push 成功才算获得，
   中间态、未知结果和 stale holder 都要有恢复/栅栏语义；
4. `pr create = author claim`、`begin`、允许无登记起草、`wake → claim → work` 四句话没有
   统一时点；memo 微分支也没有可机器区分的 branch lane；
5. 零 REST 下，仅凭 `refs/pull/*/head`、分支消失或 squash subject 的 `(#N)` 不能判定
   merged；freshness 也不能只写 head 而不裁定 base advance；
6. 补遗把 CLAIM 升为核心，但底稿 P1 清单没有 `claim` 命令、CLAIM writer 和相应 corpus。

建议 P1 只做一条真实竖切：**静态 assignment → author/gate CLAIM → exact
`(base, head)` VERDICT → quorum → 带结构化 merge receipt 的 squash merge**。动态派工、
wake、run、scratch、memo plumbing、standby、跨席 handoff 全部后移。

## 1. 审题清单逐条表态

### ① 三层承载失效模式 — 有条件通过

三层职责划分是对的，但“本地没看见事件”必须区分三种状态：

- 远端本来没有该 ref；
- 远端有，本地没有配置 fetch refspec 或尚未 fetch；
- 远端曾有，后来被删除/倒退。

后两种不能当作“零事件”。对只读 `status` 应输出 `INCOMPLETE_FACTS`；对 `claim`、
`verdict`、`merge` 等写/决策动作必须 fail closed。每次有副作用的命令应先：

1. `ls-remote` 取得相关远端 tip 集；
2. fetch 到独立 remote-tracking namespace；
3. 校验本地看到的 tip 与 advertised tip；
4. 验证事件链结构后再 derive。

建议远端观察落在 `refs/hctl/remotes/<remote>/events/<seat>`，不要让后台 fetch 直接改写
本地 publishing ref。publishing ref 与 remote-tracking tip 不相等时，表示有一笔未决发布，
其他本地 writer 必须先恢复它，不能继续 append。

事件链需要逐 ref 验证：

- root 为约定的 genesis；其后每个 event commit 恰有一个 parent；
- parent 必须是前一 tip，不接受 merge commit；
- commit tree 恰含一个 `event.json`；
- JSON 通过对应版本 schema，payload seat 与 ref seat 相同；
- 任一坏 event 都使该 ref quarantine，不能“忽略坏 suffix 后继续 merge”。

**误删/倒退**是当前最危险的未写明路径。默认 fetch 通常不会替用户证明远端 deletion，
而 `--prune` 又可能把本地最后一份证据清掉。doctor 应比较远端/本地 ref 集：发现远端 ref
消失或非 fast-forward 时保留本地 tip 到 recovery namespace，报完整性错误，等待 forward-only
修复；不能自动把 deletion 解释成清空历史。free private repo 下无服务端保护，这仍属于
“防误操作、不防恶意”的信任边界。

“先合 memo、后 VERDICT”应由 writer 拒绝并由 derive 二次验证。`memo` 不能只是 path，
至少要钉 `{commit, path, blob}`；只有 commit 已可达于所声明 base branch 且 path 对应 blob
时才有效。若事件先到、memo 后到，事件在此期间不满足 quorum；不要让一个裸 path 在未来
偶然出现后静默变有效。

链增长在 P1 不是阻断项。先用 tip-keyed 可丢缓存做增量读取，语义仍由全链重建；不要在尚无
数据前设计 compaction。未来若分段，必须用前段 tip anchor 连起来，不能重写既有链。

### ② git notes vs event commit chain — 选择后者

结论：使用**custom ref 下的一事件一 commit 的线性链**，不使用 git notes 作为统一事件基质。
“裸 ref 链”这个叫法不精确；ref 必须指向对象，建议规范中称 **event commit chain**。

git-appraise 证明了“review 元数据可完全放在 Git objects/refs、无需服务端”这一上层判断，
但它的具体 notes 形态不适合 hctl：

- git-appraise 把一条 JSON 放一行，按 annotated revision 聚合，多写者 pull 时用
  `cat_sort_uniq` 合并；这是可交换的评论集合，不是互斥日志；
- notes 对 VERDICT 钉 revision 很自然，但 EDGE、CLAIM、CANCEL、presence NOTE 没有天然
  annotated object；
- 同一 head 上多次 verdict/claim 只能塞进同一 note blob，再自行恢复事件 identity 与顺序；
- notes merge 的 union/cat-sort 语义会主动消去线性先后，不能承担 CLAIM winner；
- notes ref 本身仍是 commit/tree 历史，跨机写同一 notes ref 仍需处理 push 竞态，并没有省掉
  CAS 层。

建议每个 event commit 的 tree 只含 `event.json`，commit message 放人读摘要。parent 提供席内
全序，event JSON 提供机器语义，event commit OID 可作后续引用。不要把唯一 payload 塞在
commit message 中，也不要让 commit author/committer 身份参与 seat 判定。

参考实现与语义：

- [git-appraise metadata](https://github.com/google/git-appraise#metadata)
- [git-appraise request schema](https://github.com/google/git-appraise/blob/master/schema/request.json)
- [git-appraise comment schema](https://github.com/google/git-appraise/blob/master/schema/comment.json)
- [git notes 官方文档](https://git-scm.com/docs/git-notes)

### ③ slot 边界案例 — 机制可行，时点需重写

先区分“本地起草”与“获得发布权”：

- 两机各自 `begin` 一个未发布草稿，可以允许；它们没有共享 index，也没有远端正式事实；
- 第一次 push task branch / create PR 之前，必须先取得 author obligation 的 CLAIM；
- CLAIM 胜者才可发布；败者保留本地草稿或转 memo，不得创建第二个 author PR。

这保留“写锁在发布、不在思考”，也修正“所有义务都先 claim 再 work”的过度概括：gate 等
昂贵重复劳动应先 claim；author 可以先本地 speculative draft，但必须先 claim 再产生远端
副作用。若希望 `begin` 本身就代表正式开工，则 `begin` 必须先远端 claim，不能两种含义并存。

`pr create = claim` 不能按字面实现为“先调用 GitHub，再视为取得锁”，因为两个 clone 可以
各自成功创建不同 PR。正确顺序是：

1. append author CLAIM 并成功推到 seat ref；
2. push/adopt task branch；
3. `gh pr create`；
4. 后续状态以 claim + branch/PR head 关联。

provider-hosted 自动分支先视为 unclaimed proposal；需要 `hctl begin --adopt <branch>` 一类
动作取得 slot 后才可进入正式 author 流程。

memo lane 必须在 branch namespace 上结构可分。现有 `work/<seat>/*` 同时容纳 author 和
`work/claude/memo-*`，而 K-08 又说 derive 从分支名直推归属；这无法证明 memo 不占 slot。
建议：

```text
refs/heads/work/<seat>/<slug>    # author-class
refs/heads/memo/<seat>/<slug>    # memo lane
```

seats 配置分别声明 `author_branch_patterns` 与 `memo_branch_patterns`，doctor 检查各席 pattern
两两不重叠。memo PR 永不改变 author branch head。

P1 把 `author_concurrency` 固定为 1；字段可存在但 schema 只接受 0/1。大于 1 会改变 slot
代数与 status 输出，等真实需求再开放。

同席跨机 HANDOFF 在 P1 只转执行化身，不换 branch、不换 seat；跨席 author handoff 会破坏
“branch namespace 直推 author”假设，应延后裁定。

### ④ wake 经济学 — 语义通过，实现需 clone 级合并轮询

30 秒一次意味着每个永久 `wake` 每小时 120 次 Git transport：

- 6 个席独立轮询：720 次/小时，17,280 次/天；
- 两台机器各 6 个化身：1,440 次/小时，34,560 次/天。

这不是 REST rate-limit，却仍是无必要的 SSH/TLS/process 压力。`.git` 共享本身不会自动让六个
waiting process 共享某一次 `ls-remote` 结果；必须显式做 clone-local coalescing。

建议 P2：

- `.git/hctl/` 内用短期 poll lease + snapshot generation；
- 每个 clone 同一时刻最多一个进程 `ls-remote`，其余 wake 读共享 snapshot；
- leader 只是一轮 poll 的角色，不是 daemon；退出后任意 waiter 可接；
- active 30 秒，standby 可指数退避并加 jitter；
- 只查 main、work/memo、PR head 和 hctl event refs，不扫无关 tags；
- event tip 不变时使用 tip-keyed derived cache，cache 可删。

合并后单 clone 是 120 次/小时，两 clone 是 240 次/小时。poll tick 本身不调用 LLM；`wake`
应在进程内阻塞多个 tick，只在 attention set 改变或长 timeout 时返回。若每 30 秒退出让模型
重发命令，才会制造真实 token 浪费。

### ⑤ derive 可判定性 — 现案不闭环

quorum 可从 assignment + event chains 机械推导；GitHub PR 生命周期不能完全从普通 Git
refs 推导。

本仓实测：已 squash-merged 的 PR #1、#2、#3 的 `refs/pull/<n>/head` 仍全部存在。因此：

- PR head ref 存在不等于 open；
- task branch 消失既可能 merged，也可能 closed/deleted；
- squash commit 不是 PR head 的 descendant；
- squash subject 中 `(#N)` 是可编辑文本，以 regex 解析会违反 K-03。

GitHub 也说明 PR head/merge refs 是临时只读 refs，而 merge ref 的刷新有平台时机约束，不能把
它当权威 merge receipt：

- [GitHub pull request refs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests#pull-request-refs)
- [GitHub 关于 merge ref 可陈旧的说明](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-your-git-database#checking-mergeability-of-pull-requests)

零额外 REST 的可恢复闭环是让 `hctl merge` 控制 squash message，向落在 main 的 commit body
写机器 trailer：

```text
Hctl-Work: <work-id>@<work-blob-oid>
Hctl-PR: <number>
Hctl-Base: <full-oid>
Hctl-Head: <full-oid>
Hctl-Claim: <claim-event-oid>
```

`gh pr merge --squash --match-head-commit <head> --subject ... --body-file ...` 已有精确 head
precondition 与自定义 body。调用成功后 fetch main，只有 trailer 全匹配才 derive `merged`。
若进程在 GitHub 已 merge、写本地状态前崩溃，main trailer 仍可恢复。绕过 hctl 的网页 merge
被归类为 `UNRECORDED_MERGE`，需审计/forward-only 补记，不能猜。

还缺 base freshness 的裁定。只钉 head 不够：main 前进时，GitHub 的 squash 结果和 review
时的比较基线可能改变。VERDICT 应钉 revision tuple `{base, head}`。P1 可先取严格规则：
required verdict 的 base/head 都必须与 merge 前 snapshot 一致；后续若要允许 base advance，
需成为明示 policy 并有 corpus，不能默认放行。

严格 base 规则还带来 merge TOCTOU：多个 seat 同时 merge 时，检查后的 main 可能先被别人推进。
P0 必须在以下方案中选一项：

- 指定单一 merge coordinator/serialization obligation；
- 增加一条短时全局 merge CAS；
- 使用可用的 GitHub merge queue；
- 明确接受 head-only freshness，并把 base advance 风险写入法律。

当前文本没有选，不能宣称 merge 判定已闭环。

### ⑥ 三个 schema 字段级设计 — 当前仅有名目；建议如下

统一要求：

- JSON Schema draft 2020-12；
- 所有机器对象 `additionalProperties: false`；
- OID 接受当前 SHA-1 与未来 SHA-256 全长，不接受缩写；
- 所有集合设 `uniqueItems`，所有枚举大小写固定；
- JSON Schema 管单对象形状；跨文件唯一性、DAG 无环、pattern 不重叠、ref/object 可达性由
  `doctor`/loader 管，不能假装 schema 能做到；
- schema version 与 hctl binary version 分开。

#### ⑥-A `seats.schema.json`

建议配置根字段：

| 字段 | 类型 / 是否必需 | 约束与语义 |
|---|---|---|
| `schema_version` | integer / 必需 | P0 定稿后 `const: 1`；替代含义模糊的 `version = 0` |
| `kernel` | string / 必需 | 精确 semver 或 Git OID pin；bootstrap 可临时允许 `hctl@bootstrap` |
| `seats` | object / 必需 | key 即 seat id；key 限 `[a-z][a-z0-9-]{0,31}` |

每个 seat：

| 字段 | 类型 / 是否必需 | 约束与语义 |
|---|---|---|
| `harness` | string / 必需 | 开放 registry id，不硬编码厂家排名 |
| `model` | string / 必需 | 实际模型标识；归因与能力说明，不参与路由猜测 |
| `capabilities` | unique string[] / 必需 | planner hint；P1 内核只校验引用存在 |
| `write_scope` | enum / 必需 | `canonical` / `memo-only`；比当前 `write` 更不含糊 |
| `author_concurrency` | integer / 必需 | P1：canonical=`1`，memo-only=`0` |
| `author_branch_patterns` | string[] / 条件必需 | 完整 `refs/heads/...` pattern；canonical 至少一项 |
| `memo_branch_patterns` | string[] / 必需 | 推荐唯一标准形 `refs/heads/memo/<seat>/*` |
| `token_class` | enum / 可选 | `full` / `limited`；纯排班 metadata |
| `features` | object / 必需 | 把当前 TOML comments 变成可验证数据 |

`features` 至少分开：

```text
session_resume    = yes | no | limited | unknown
parallel_sessions = yes | no | limited | unknown
subagents         = yes | no | limited | unknown
skill             = native | adapter | unsupported | unknown
door_file         = <filename>
```

删除 `memo_prefix`：它应从 seat id 唯一派生为 `<seat>-`，多存一份只会漂移。branch pattern
采用何种 grammar 必须定死；建议只允许 Git refspec 风格的单 `*` pattern，不开放 Python
regex 或含糊 glob。

schema 外的 doctor 规则：

- 所有 author/memo patterns 跨席、跨 lane 两两不重叠；
- `memo-only` 不得有 author pattern；
- 同一 `(harness, model)` 被拆成多个可投票 seat 时警告或要求显式 `vote_identity`，防同一颗
  脑子意外算两票；
- branch 实际 owner 必须唯一；
- machine/session 不得进入本文件。

#### ⑥-B `edge.schema.json`

**不建议以当前语义保留这个名字。**图的 edge 应至少有 `from`/`to`；当前对象实际上是
“一个有 dependencies、author、gates 和 merge policy 的工作项”，即 graph node /
assignment。继续叫 edge 会让 schema 从第一天就名实不符。建议改为
`assignment.schema.json`（比被否决的 compiled WorkOrder 更轻），目录改
`.hctl/assignments/`，动态事件名由 `EDGE` 改 `ASSIGN`。

若暂时保留文件名，字段也应按 assignment 定义：

| 字段 | 类型 / 是否必需 | 约束与语义 |
|---|---|---|
| `schema_version` | integer / 必需 | `const: 1` |
| `id` | string / 必需 | 项目内稳定 id；不可含 machine/session |
| `kind` | enum / 必需 | P1 只开 `change`；以后再开 `consult`/`closeout` |
| `needs` | unique string[] / 必需 | 前置 assignment ids；loader 查存在与无环 |
| `base_ref` | full ref string / 必需 | 例如 `refs/heads/main` |
| `author` | object / 必需 | `{seat, branch_slug, claim_timeout_seconds}` |
| `gates` | object[] / 必需 | gate id + requirement AST + 四轴 |
| `merge` | object / 必需 | P1 `{method:"squash"}`，并声明谁有 merge obligation |

每个 gate：

| 字段 | 类型 / 是否必需 | 约束与语义 |
|---|---|---|
| `id` | string / 必需 | assignment 内唯一 |
| `mode` | enum / 必需 | `required` / `advisory` / `observe` |
| `requirement` | object / 必需 | 结构化 AST，不用自由文本表达式 |
| `threshold` | enum / 必需 | 暂沿用 `P0` / `P1` / `all`，METHOD 必须定义排序 |
| `on_timeout` | discriminated object / 必需 | `escalate` / `deputy` / `proceed` |
| `claim_timeout_seconds` | positive integer / 必需 | 只用于 overdue/reclaim eligibility |

quorum AST 只开放有限节点：

```json
{"seat": "codex"}
{"all_of": [{"seat": "codex"}, {"seat": "grok"}]}
{"any_of": [{"seat": "codex"}, {"seat": "grok"}]}
{"at_least": {"count": 2, "of": [{"seat": "codex"}, {"seat": "grok"}, {"seat": "glm"}]}}
```

禁止 `"codex && (grok || glm)"` 字符串语言。loader 还要拒绝重复 leaf、未知 seat、空集合、
`count > len(of)`、required+proceed、deputy 不在允许集合等跨字段错误。

静态 assignment 的 revision identity 是 `{main_commit, path, blob_oid}`；动态 assignment
的 identity 是其 ASSIGN event commit OID。不要把自指 content hash 塞回 JSON。

obligation id 由工具生成，不由 LLM 起名。推荐逻辑键：

```text
<assignment-revision>#author:<seat>
<assignment-revision>#gate:<gate-id>:<seat>:<base-oid>:<head-oid>
<assignment-revision>#merge
```

实际 wire 可把该规范化 tuple hash 成短显示 id，但事件中仍保留可审计的结构化 tuple。gate
把 base/head 纳入 identity 后，head 或严格 base 变化会自然产生新 obligation，旧 verdict
不会误复用。

#### ⑥-C `event.schema.json`

使用 common envelope + 以 `type` 判别的 `oneOf`；不能做“六类字段全 optional”的大对象。

common envelope：

| 字段 | 类型 / 是否必需 | 约束与语义 |
|---|---|---|
| `schema_version` | integer / 必需 | `const: 1` |
| `event_id` | UUID / 必需 | client 生成，处理 push 结果未知时的幂等查找；不承担排序 |
| `type` | enum / 必需 | VERDICT / ASSIGN(若暂不改则 EDGE) / HANDOFF / CANCEL / NOTE / CLAIM |
| `actor` | object / 必需 | `{seat, machine, session}`；seat 必须等于 ref owner |
| `created_at` | RFC 3339 UTC / 必需 | 工具生成；超时计算需考虑 clock skew |

`actor.machine` 建议是 hctl installation UUID 或不含隐私的 alias，不直接默认为 hostname；
`actor.session` 允许 `null`，见第⑫项。两者只做 provenance，不能进 quorum、ownership 或
freshness。

各 event 必需字段：

- `CLAIM`
  - `obligation`：完整规范化 obligation key；
  - `reclaim_of`：首次 claim 为 null；reclaim 时为当前 active claim event OID；
  - `reclaim_reason`：首次为 null；其后枚举 `overdue` / `handoff` / `operator`;
  - `reclaim_after`：RFC 3339；是可显式 re-claim 的最早时刻，不是后台自动动作。
- `VERDICT`
  - `obligation`、`claim`（active CLAIM event OID）；
  - `pr`（positive integer）；
  - `revision: {base, head}`（full OIDs）；
  - `decision: APPROVE | REQUEST_CHANGES`；
  - `max_severity: NONE | P0 | P1 | P2`；
  - `report: {commit, path, blob}`。
- `ASSIGN` / `EDGE`
  - 完整 assignment payload；
  - 不要求 head；event commit OID 即动态 assignment revision。
- `HANDOFF`
  - `obligation`、`claim`、`to: {seat, machine?, session?}`、`reason`；
  - HANDOFF 关闭旧 claim，接收者仍需新 CLAIM，不能凭 prose 直接占有。
- `CANCEL`
  - discriminated `target`：assignment / obligation / claim；
  - `reason`；
  - authority 由 METHOD + seats policy 校验，不能默认任一 seat 可取消任意工作。
- `NOTE`
  - `category`、`subject`、可选 `report`/短 message；
  - 法律上永不满足 gate、永不释放 slot、永不触发 merge，否则它就不是 NOTE。

不是每类事件都钉 head。正确法律是：**凡结论依赖某 revision，必须钉完整 revision tuple**。
VERDICT 必须；CLAIM 是否带 revision 由 obligation kind 决定；ASSIGN/EDGE、presence NOTE 和
取消尚未产生 head 的 assignment 不应伪造 head。

threshold 还有一个语义坑必须在 METHOD 定案：若 reviewer 给
`REQUEST_CHANGES + max_severity=P1`，而 gate threshold 是 P0，它到底满足 gate 还是不满足？
建议 `decision` 是 reviewer 按本 gate threshold 作出的最终决定；不允许内核凭
`max_severity` 覆写 decision。CLI 展示 threshold 后只让 reviewer选
APPROVE/REQUEST_CHANGES，finding 细节留 memo。

### ⑦ 执行等级漏防 — 原则通过，表尚不完整

至少补以下不变量与执行级：

| 不变量 | 建议级别 | 机械措施 |
|---|---:|---|
| 相关远端 refs 已完整 fetch | ②拒绝 | 写动作前比较 advertised/fetched tips |
| event chain 单 parent、schema 合法、seat 对 ref | ①/② | writer 构造；reader quarantine |
| event ref 不倒退/不消失 | ③审计 | doctor 比较远端、本地与 recovery anchors |
| memo pointer 已合并且 blob 匹配 | ②拒绝 | verdict writer + derive 双检 |
| gater ≠ author、同 seat 只计一票 | ②拒绝 | obligation/evaluator 集合语义 |
| verdict 绑定 current claim 与 base/head | ②拒绝 | event validator + merge check |
| stale claimant 不可发布结果 | ②拒绝 | 每次副作用前 refetch；result 携 fencing claim OID |
| author/memo branch lane 不混淆 | ①/② | 不相交 namespace + doctor |
| required timeout 不 silent proceed | ①/② | schema 排除组合 + evaluator |
| merge 有结构化 receipt | ②拒绝 | hctl 控制 squash body；无 receipt 报审计债 |
| 直接网页/裸 gh 绕过 hctl | ③审计 | main 新 commit 无 Hctl trailers 时报警 |

| event/date/trailer 不由 LLM 猜 | ②拒绝 | hctl 生成；adapter 无证据时拒绝或显式 unknown |

“overdue → re-claim”不能只靠两个客户端时钟变成自动安全结论。零 REST/零 server
timestamp 下没有可信公共时钟；reclaim 必须显式、有宽限，并依赖 fencing token 阻止旧 claimant
的后续机器动作。纯本地编辑无法被远端锁阻止，这属于已声明信任边界。

此外，Git hooks 不随 clone 自动启用，`core.hooksPath` 也属于本地配置；adopter template +
doctor 是三级审计，不是一级结构不可能。P0 执行等级表应如实标注。

### ⑧ 命令面与 naming — 需调整

补遗引入核心 CLAIM，却没有 `hctl claim`，这是直接缺口。建议 P1 命令只有：

```text
hctl doctor
```

其中 `begin` 的语义必须二选一并写死：

我偏向 formal 默认，另给显式 `--draft-only`，避免弱 harness 把本地成功误报成已接活。

- `EDGE`：当前不是 graph edge，改 `ASSIGN`/assignment；
- `wake`：实际行为是阻塞等待变化，行业词 `wait`/`watch` 更直观；若保留 wake，help 必须明确

- `verdict`：可保留，值使用 GitHub `APPROVE` / `REQUEST_CHANGES`；
- `reconcile`：不另设动词是对的，status 每次 reconcile；
- `run`：会启动/恢复 harness，与 K-13“不开 harness、不是编排器”有张力；移到 adapter

- `recover` 不必另开泛化动词；CLAIM 用显式 reclaim，event publish 中间态由每个写命令内部
  recover，doctor 只报告。

`seat` 与 `memo lane` 的自造有充分理由；`attention set`、assignment、claim、quorum、

### ⑪ CLAIM 机制攻击面 — 两阶段 CAS 可行，需恢复与 fencing

#### ⑪-A 判定

**可行，但应改名“两阶段 CAS append”；只有远端 CAS 成功才算 claim acquired。**

我用一个临时 bare remote、两个独立 clone 做了最小实证：

- 同 clone 两个候选都基于 tip `R`，第一个
  `git update-ref refs/coop/codex C1 R` 成功，第二个以 status 128 失败；
- 两 clone 各自本地 CAS 都成功后，第一个用 explicit expected tip push 成功，第二个
  remote push 以 status 1 被拒；
- 远端最终 tip 只含 winner。

这验证了 mutex 的核心，但没有把 local update 与 network push 变成一个事务。规范算法应为：

1. fetch remote seat ref 到独立 remote-tracking ref，得精确 tip `R`；
2. 验证 publishing ref 也等于 `R`；不等则先恢复上一笔未决发布；
3. 在 `R` 的事实 snapshot 上 derive，确认 obligation 可 claim、author slot 可用；
4. 生成 event JSON 与一-parent commit `C(parent=R)`；
5. 本地 CAS：`git update-ref <publishing-ref> C R`；
6. 远端 CAS：
   `git push --force-with-lease=<remote-ref>:R origin C:<remote-ref>`；
7. push success 后更新/重新 fetch remote-tracking tip，才返回 acquired。

必须使用带**显式 expected OID**的 lease，不能用隐式 remote-tracking lease；Git 官方文档也
明确区分了二者：

- [git update-ref](https://git-scm.com/docs/git-update-ref)
- [git push --force-with-lease](https://git-scm.com/docs/git-push)

`--force-with-lease` 在这里不是允许改写历史；`C` 仍必须是 `R` 的单 parent，lease 只把
“remote 仍精确等于 R”写成协议 precondition。server 若支持原子 compare-and-swap，
winner 唯一。

#### ⑪-B 中间态恢复

至少处理：

- **local CAS 成功，尚未 push 就崩溃**：publishing tip `C`、remote tracking `R`。下个 writer
  识别未决 transaction，验证 C 后可补 push；不能继续 append。
- **push 成功，客户端没收到成功**：重新 fetch；若 remote chain 中找到 `event_id`，视为成功，
  不重复写。
- **push 被另一机器抢先**：fetch winner `D`；若 publishing ref 仍为 `C`，CAS reset 到 `D`；
  C 留作 unreachable object，不能 merge 两个 claim。
- **remote ref 被删除/倒退**：进入 integrity error，不按普通 lease loss 自动重建空链。
- **同机第二 writer 看见 local C 但 remote 仍 R**：不得把 local unpublished event 当事实；
  remote-tracking snapshot 才是已发布事实。

这样 local CAS 本身兼任 durable publish journal。若实现允许第二 writer 在
`publishing != remote-tracking` 时继续 append，就需要额外本地锁；更简单的 P1 是直接拒绝。

#### ⑪-C CLAIM 不是永久所有权：需要 fencing

claim event OID 是 fencing token。所有能完成义务的事件（至少 VERDICT/HANDOFF）必须引用
active claim OID；每个 remote side effect 前 refetch 并确认 token 仍 active。derive 拒绝来自
stale claim 的 verdict，即使 JSON 本身合法。

author 的本地编辑无法被 Git ref 锁禁止。P1 能机械拦的是通过 hctl 的 publish/merge；裸
`git push` 仍是信任边界。正常路径上，同 branch 的 non-ff push 再提供一层防撞，但它不能替代
claim check。

#### ⑪-D overdue/re-claim 与震荡

不做自动 re-claim loop。`reclaim_after` 只令 attention set 显示 eligible；另一化身必须显式：

```text
hctl claim <obligation> --reclaim <current-claim-oid>
```

writer 校验：

- current active claim 精确等于参数；
- now 已过 reclaim_after + 允许的 skew grace；
- 没有有效 completion event；
- 新 CLAIM parent 是刚 fetch 的 seat tip。

两个化身同时 reclaim，远端 CAS 仍只允许一个。旧 claimant 恢复后因为 fencing token 失效，
不得发布；它不能再自动把 obligation 抢回。若要重新取得，只能当前 winner handoff、再次
overdue 后由 operator 显式动作，避免 A/B 自循环震荡。

CLAIM 不续租、不写 heartbeat，链增长只来自真实状态转换。若任务常常超过 timeout，应调整
assignment policy，而不是发 NOTE 保活。

### ⑫ 化身模型与 session 来源 — 身份模型通过，session 不作 correctness 前置

`seat（投票身份）→ incarnation（machine×session provenance）→ local worktree → task
branch → active claim` 这条链是清楚的。quorum 只按 seat 去重正确；machine 不进 branch、
memo、ref 或 obligation id 也正确。

需要把“同席双机只有 origin 相交”限定为两个独立 clone；同机多 worktree 共享 `.git`，所以
恰好需要本地 CAS。两物理模型不应混写。

#### ⑫-A session 字段来源

各 harness 未必暴露稳定 native session id，resume 后含义也可能不同。建议：

- `machine`：hctl 生成的 installation UUID（可配人读 alias），仅 provenance；
- `session`：由 harness adapter / `hctl run` 提供的 hctl run UUID；
- native provider session id 若可得，未来放可选扩展字段，不拿它做互斥；
- 无 adapter 时 `session: null` 合法并醒目展示；
- CLAIM event OID 才是 correctness identity。

不要把一个“current session id”写进共享 `.git/hctl/current`：同机多 tab 会互相覆盖。若
`hctl run` 不属于 kernel，则由每个 tab 的环境变量传入；拿不到就 null，不猜。

- 自动加载文件名；

- root/nested 文件的优先级与覆盖规则；
