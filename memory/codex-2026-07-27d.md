## 2. F3：rebind claim 在 merge 后自我失效

### 2.1 反例

设 coordinator 配置文件在 base `B0` 的 blob 为 `C0`，旧 coordinator 为 A：

```text
A claim rebind PR at {base=B0, config=C0}
→ A 经唯一 merge slot 将 rebind PR squash 到 M
→ M 内 config blob 变为 C1，coordinator=B
→ fetch main；当前 config=C1
→ 27g 规则：C0 != current C1，因此该 merge claim stale
→ receipt 引用的已不是 active claim，按 claim-OID fencing 被拒
```

这不只影响“换 coordinator”的 PR。任何修改同一 config blob 的 `.hctl/**` PR 都会在自身
merge 后触发 `C0 != C1`；而 receipt 本来就只能在 merge、fetch、post-verify 后写入，因此
不能靠“更快写 receipt”消除窗口。

旧 coordinator 单链 capacity=1 确实保证了 **merge 前** 的互斥，这部分批准；问题只在
cutover 后如何合法终结旧 claim。

### 2.2 最小修复

把 config revision 的校验拆成两个时点：

```text
claim / pre-merge:
    coordinator_config_revision MUST equal config blob at current main/base
    actor seat MUST equal coordinator named by that revision

post-merge receipt:
    coordinator_config_revision MUST equal config blob at Hctl-Base
    merge claim MUST have been active in the pre-merge fact snapshot
    receipt MAY close that claim even if the merge result changes config

new claim after merge:
    MUST use config at current main
    MUST target the coordinator named by the new revision
```

也可显式派生一个 `merged_pending_receipt` 终态前状态：merge 已由 main/receipt preimage
证明发生，旧 claim 不再占新 coordinator 的 slot，但只有对应 receipt 能关闭审计债。

`coordinator_config_revision` 还应明确是哪个固定配置 path 的 blob，或像 F1 一样使用
`{commit,path,blob}` source；“.hctl 配置 blob”不能指一个目录。

### 2.3 必测 corpus

1. 普通 `.hctl` config PR：merge 改 blob 后，receipt 仍可按 `Hctl-Base` 的 C0 关闭 claim；
2. rebind A→B：M 前只有 A 可 claim，M 后只有 B 可 claim；
3. A 的旧 worker 基于 C0 在 M 后尝试新 claim：级②拒绝；
4. receipt 若声称的 config revision 不等于 `Hctl-Base` 所见 blob：拒绝。

## 3. F4：锚点不同不等于因果前进

27g 已正确规定：

- escalated 后进度不解冻；
- streak 只读链上 accepted claims；
- author claim 增 `tip_at_claim`；
- 不依赖墙钟或跨 ref 采样顺序。

尚未闭合的是：

```text
anchor_old != anchor_new  ⇏  anchor_new is progress from anchor_old
```

两个可重放反例：

1. author/gate head 在 H1→H2→H1 间来回切换，每次 OID 都与相邻值不同，streak 永远重置；
2. 非 fast-forward 改写或回卷也产生新 OID，却不是“git 事实前进”。

此外，gate/merge 直接比较整个 `{base,head}` 会把“仅 base 因别的 PR 前进”自动记成该义务的
工作进度。它可以被政策裁成“环境重置”，但不能无说明地叫 claimant progress。

最小确定函数应区分：

```text
forward_head_progress =
    old.head != new.head
    && git merge-base --is-ancestor old.head new.head

forward_author_progress =
    old.tip != null
    && new.tip != null
    && old.tip != new.tip
    && git merge-base --is-ancestor old.tip new.tip

base_only_change =
    old.head == new.head && old.base != new.base
```

- forward progress 才清 streak；
- same 或 non-FF 不清，并另报 rollback/rewrite；
- base-only 是否重置须明确命名为 environment reset，并单独裁定，不能混进“锚点变化”；
- initial author claim 的 `tip_at_claim` 允许 null，branch 建立后的 re-claim 才作 ancestry 比较；
- 若产品希望把合法 force-push 算进度，该事实不可由 ancestry 机械证明，应走显式、
  可审计的 progress marker，而不是把所有“不等”放行。

这仍是状态/derive 逻辑，不增加事件类型，也不扩大 P1。

## 4. F5：RFC 8785 不做 Unicode normalization

JCS 是合适的 canonical JSON 选择；它会固定属性排序和 JSON 字符串的转义序列。但
[RFC 8785 §3.1](https://www.rfc-editor.org/rfc/rfc8785.html#section-3.1) 明确要求保留
Unicode string data 原样，**不处理 Unicode normalization**。因此：

- `"\u0061"` 与 `"a"` 解析为同一 code point，JCS 后可以得到同一 bytes；
- NFC `"é"` 与 NFD `"e\u0301"` 是不同 code-point sequence，JCS 本身会给不同 bytes/id。

27g 的“key order / Unicode / escape 变体必须同 id”若把 Unicode 变体含作 NFC/NFD 等价，
测试将与所选 RFC 冲突。

P1 最小修复二选一：

1. **推荐：identity-bearing token 限 ASCII grammar。**seat、logical id、branch slug、
   gate id 若本来就可限 ASCII，则 JCS 只需处理结构/escape，零 Unicode 等价歧义；
2. 若必须允许 Unicode，schema 在 JCS 前钉 NFC，并规定 writer/loader 对非 NFC 是统一拒绝
   还是统一正规化；NFC 是 hctl 的 schema preprocessing，不得归功于 JCS。

还须从“非规范输入拒绝**或**先规范化”中选一个规范行为。推荐：

```text
parse valid I-JSON
→ validate schema and token normalization policy
→ derive JCS bytes
→ recompute and compare obligation_id
```

如此 wire JSON 可以有不同空白/key order/escape 写法，但 identity 永远由解析后的对象经 JCS
产生；duplicate keys、非法 Unicode/I-JSON 直接拒绝。若改选“event.json bytes 必须已是
JCS”，也可行，但必须唯一化，不能让两种 reader 各自任选。

建议测试向量改成：

1. key order、whitespace、等价 JSON escape → 同 id；
2. NFC/NFD → 按 hctl schema policy 得到明确结果，不能假定 JCS 自动合并；
3. duplicate key、lone surrogate、非 I-JSON → 拒绝；
4. aspect 的结构字段次序不同 → JCS 后同 id。
