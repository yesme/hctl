# Codex Memory 2026-07-28c — Discussion kernel 提案：以最终产物为中心

> 性质：activation 前的设计提案，供后续席位加入讨论；**不是裁定、assignment
> 或 gate verdict**。
> 目标：补上 hctl 尚未建模的 discussion/consult 关系与 memo 生命周期，并让
> Git/GitHub 完全退到 kernel 内部。
> 会话实况：Codex / GPT-5.6 Sol / max effort。

## 0. 一句话方案

> Discussion 不是“一组 memo”，而是一条通向明确 outcome 的控制流；个人 memo
> 只是输入，synthesis 是候选结论，只有 resolution 所承诺的最终产物已经落地，
> 或用户记录了明确的无产物终态，discussion 才算关闭。

因此，discussion 必须在打开时声明 `outcome_contract`；hctl 根据事实给出唯一
下一步，不再让 LLM 自己解释“这篇 memo 应该即合还是等待”。

## 1. 当前缺口

当前 hctl 只建模了围绕 code/document PR 的关系：

```text
assignment → author → gate(s) → merge
```

它没有建模：

```text
brief → N 个参与席独立贡献 → synthesis → resolution → outcome
```

现状的具体证据：

1. D-11 已定义“同一 brief 扇出 N 席各自落 memo 再综合”，但 `consult` obligation
   被推迟到 P2。
2. D-43 文字上列过 `memo` helper，实际二进制没有 `hctl memo`。
3. D-44 又明确把 memo plumbing 和 consult kind 推迟到 P2。
4. kernel 只认 `memo/<seat>/*` 与 `memory/*` 的形状，不知道 memo 属于哪个
   discussion、扮演什么角色、应等待什么 barrier。
5. `hctl verdict` 要求 report memo 已经在 revision base 可达；METHOD §8.3
   又要求 verdict memo 暂不合、等一轮批合。active 模式下两者没有完整时序。

所以今天出现的多种解释不是偶然：

- 有人按“当前是否有 gate round”判断；
- 有人按“这是讨论 memo 还是 verdict memo”判断；
- 有人按“是否需要保持独立投稿”判断。

这些分类都没有进入 hctl 事实层。让 LLM 继续选择其中一种，只会继续制造漂移。

## 2. 先回答关键问题：discussion 最后落在哪里

PR 的最终落点通常是代码或文档。Discussion 的最终落点不应被固定成“又一篇
memo”，而应是一个 **resolution package**。

```text
resolution_package = {
  discussion,
  frozen_inputs,
  synthesis,
  disposition,
  outcome_refs,
  followups,
  resolver
}
```

其中：

- `frozen_inputs`：本轮确切采用的各席 contribution OID；
- `synthesis`：综合稿的不可变 artifact；
- `disposition`：`accepted / no_change / deferred / canceled`；
- `outcome_refs`：最终产物的可验证指针；
- `followups`：由结论新生的 assignment/obligation；
- `resolver`：有权作最终取舍的人或预声明 resolver。

### 2.1 最终产物可以是什么

accepted resolution 的 `outcome_contract.deliverables[].kind` 应至少支持：

| kind | discussion 的最终产物 | 关闭证据 |
|---|---|---|
| `canonical_change` | 代码、METHOD、DECISIONS、schema 等 canonical path | 对应 PR 的合规 merge receipt |
| `assignment` | 一个或多个后续工作授权 | ASSIGN/静态 assignment 的可验证 source |
| `answer` | 一份被指定为最终答案的 synthesis | synthesis 已归档且 RESOLVE 接受 |

一个 contract 可要求多个 deliverable，并用结构化 `all_of/any_of` 表达 closure。
`no_change / deferred / canceled` 则是替代 accepted 的 terminal disposition：

- `no_change` 必须说明为何不改；
- `deferred` 必须给 reopen 条件与 owner；
- `canceled` 是用户终止，不是假装形成了结论；
- `escalated` 不是关闭态，而是等待用户裁决的阻塞态。

### 2.2 为什么必须围绕 outcome 设计

如果只围绕 memo 设计，系统最多知道“大家都发言了”，却不知道：

- 讨论到底要回答什么；
- 谁负责综合；
- 谁能拍板；
- 拍板后要改哪份 canonical 产物；
- 是产生工作，还是明确不做；
- 何时算真正结束。

因此，“全部 memo 已提交”只能是 input barrier，不能是 discussion closure。

### 2.3 contribution、synthesis、resolution 三者不能混

- **Contribution memo**：某一席的独立输入；没有权威性。
- **Synthesis**：综合者提出的候选结论；仍可被 resolver 否决或改判。
- **Resolution**：把结论绑定到最终产物或明确终态的控制事实。

如果一份所谓 memo 能授权下一步，它就不是 advisory memo，而是 assignment /
resolution 等控制事实；禁止再发明“授权 memo 例外”。

## 3. Discussion 打开时的 outcome contract

建议 `DISCUSSION_OPEN` 至少冻结以下字段：

```yaml
id: pre-activation-retro
brief:
  source: {commit, path, blob}
participants:
  requirement:
    all_of: [claude, codex, grok]
  mode: independent
synthesizer: claude
resolver:
  kind: user
on_timeout: escalate
outcome_contract:
  deliverables:
    - id: canonical-spec
      kind: canonical_change
      targets:
        - DECISIONS.md
        - METHOD.md
  requirement:
    all_of: [canonical-spec]
  close_when: landed
archive: required
```

关键约束：

1. `id`、participant seat、target path 等身份字段使用既有 ASCII/JCS 纪律。
2. participant requirement 复用 gate quorum AST，而不是另造布尔语言。
3. `mode=independent` 时，hctl 在本席提交前不向其展示其他席内容。
4. `outcome_contract` 冻结后，改 brief/participants/target/resolver 均产生新 revision；
   旧 submission 不自动搬运。
5. `targets` 可声明 path pattern、logical decision ID 或 assignment target；不能只写
   “讨论一下再说”。
6. 纯咨询允许 `kind=answer`，但必须点名哪份 synthesis 是最终答案。

## 4. 状态机

建议 discussion 的人读状态如下：

```text
OPEN
  ↓
COLLECTING
  ↓ all required participants submitted
READY_TO_FREEZE
  ↓ coordinator CAS freezes exact submission OIDs
FROZEN
  ↓
SYNTHESIZING
  ↓ synthesis submitted
PROPOSED
  ├─ resolver rejects / asks another bounded round → OPEN(new revision)
  ├─ unresolved conflict                         → ESCALATED
  ├─ no_change / deferred / canceled             → CLOSED
  └─ accepted
       ↓
     MATERIALIZING
       ↓ outcome closure evidence verified
     CLOSED
```

### 4.1 为什么需要显式 FREEZE

“现在看起来所有人都交了”不是稳定快照。最后一席提交的同时，第一席可能 amend。

`DISCUSSION_FREEZE` 应由单一 coordinator CAS 发布，并精确引用每席采用的
submission event OID。freeze 之后：

- synthesis 只读这组 OID；
- 原席继续 amend 会形成下一 revision，不静默替换本轮输入；
- independent veil 可以解除；
- 所有人看到同一个 discussion packet。

### 4.2 Round budget

综合稿被反驳后，不允许在同一 revision 无限横向往返。每个 discussion revision
应有显式 round budget：

- 一次 contribution fan-out；
- 一次 synthesis；
- 一次 resolver 处理。

需要新一轮时，resolver 发布新 revision，说明 reopened questions；无法裁定则
`ESCALATED`。这复用 D-41 “一轮后收口或上提”的经验。

## 5. Memo 不应天然等于 GitHub PR

当前“一篇 memo 一个 PR”把 GitHub transport 暴露给了 LLM，也让每份输入都推进
main。提案改为两层：

### 5.1 Submission artifact

`hctl memo submit`：

1. 读取本地 draft；
2. 验证当前 seat 拥有该 memo obligation；
3. 生成正确 path、metadata 和 attribution；
4. 用 Git plumbing 创建不可变 content commit；
5. CAS push 到 hctl 管理的 durable artifact ref；
6. 在本席 event chain 发布 `MEMO_SUBMITTED`，携带
   `{discussion, role, commit, path, blob}`。

这一步：

- 不创建 GitHub PR；
- 不推进 main；
- 不占 merge slot；
- 不需要其他席批准；
- 对同一 obligation 再次提交必须显式 `supersedes`。

artifact ref 的最终命名需单独 gate；原则是远端持久、seat 隔离、CAS、不可依赖
会被 GitHub 自动删除的 PR ref。

### 5.2 Batch archive

在 contribution 与 synthesis 都冻结后：

1. hctl 将 frozen artifacts 物化为 `memory/<seat>-*.md`；
2. 一次创建 discussion archive PR；
3. coordinator 通过 hctl 做 exact-head squash + post-verify；
4. resolution 引用 archive commit 与每个 blob。

因此一轮 discussion 只为归档推进 main 一次，而不是 N 篇 memo 推 N 次。

若 outcome 本身是 canonical change，archive PR 与 outcome PR 默认分开：

- archive 是证据层；
- outcome PR 是规范/代码层，进入既有 author/gate/merge DAG。

这样不会把 advisory memo 混成 canonical authority，也不会让归档文件扩大代码
review scope。

## 6. CLI：只暴露领域动作

建议命令面：

```text
hctl discuss open <id> --brief <source> --participants <expr>
    --mode <independent|open> --synthesizer <seat>
    --outcome <contract>

hctl discuss status <id> [--json]
hctl discuss wait <id>

hctl memo begin <discussion/memo-obligation>
hctl memo submit <discussion/memo-obligation> --file <draft>
hctl memo amend <submission-oid> --file <draft>

hctl discuss freeze <id>
hctl discuss show <id> <seat|all>
hctl discuss synthesize <id> --file <draft>
hctl discuss resolve <id> --accept <synthesis-oid>
hctl discuss resolve <id> --no-change|--defer|--cancel ...

hctl discuss archive <id> [--check]
hctl discuss materialize <id>
```

命令名仍可讨论；关键不是叫 open/close 还是 begin/land，而是：

- LLM 只传 discussion/obligation ID；
- 不传 `--merge-now` / `--hold` 这种重新把政策交给 LLM 的开关；
- hctl 从 frozen contract 和 event facts 推导允许动作；
- `status` 输出唯一 `next_action` 与完整 `blocked_by`；
- 所有远端副作用前后都有 exact fact 与恢复路径。

示例：

```text
$ hctl discuss status pre-activation-retro
state=COLLECTING
submitted=claude
blocked_by=contribution:codex,contribution:grok
next=hctl memo submit <codex-obligation>
```

全部提交并 freeze 后：

```text
state=FROZEN
inputs=claude@<oid>,codex@<oid>,grok@<oid>
holder=claude
next=hctl discuss synthesize pre-activation-retro
```

outcome 被接受但尚未落地时：

```text
state=MATERIALIZING
blocked_by=outcome:canonical_change
next=hctl begin <generated-assignment>
```

## 7. Git 与 GitHub 的位置

用户和 LLM 看到的调用链应当是：

```text
user / seat
    ↓ domain command
  hctl kernel
    ├─ Git plumbing
    └─ gh / GitHub transport
```

禁止把以下内容写进正常工作说明：

```text
git switch -c ...
git add / commit / push ...
gh pr create ...
gh pr merge ...
```

hctl 内部可以继续调用 `git` 和 `gh`，就像当前 `hctl merge` 内部调用
`gh pr merge`；它们是驱动，不是面向席位的 API。

### 7.1 “禁止直接 gh”能保证到什么程度

本地 kernel 无法阻止一个恶意操作者绕过它直接调用 GitHub。当前 threat model
本来就是防失误与漂移，不防恶意。

可实现的机械边界是：

- 所有正常文档只给 hctl 命令；
- hctl 生成 receipt 并 post-verify；
- main 上发现没有 hctl receipt 的 memo/archive/outcome merge，报告
  `UNRECORDED_*`；
- active 模式下后续写动作 fail-closed；
- 若未来要求物理禁止旁路，需要 GitHub branch protection/App，属于 server-side
  enforcement 的独立决策。

## 8. 与现有 PR DAG 如何衔接

Discussion 不替代现有 assignment/gate/merge；它位于其上游：

```text
discussion inputs
      ↓
   synthesis
      ↓
  user resolution
      ↓
outcome contract
      ├─ answer/no-change/deferred → discussion terminal
      └─ canonical change/assignment
                    ↓
          existing PR work DAG
                    ↓
            verified merge receipt
                    ↓
             discussion CLOSED
```

因此可以明确回答：

> 是的，discussion 应围绕最终产物设计；但不是所有 discussion 都必须产出代码。
> 它必须产出一个预先声明、可验证的 outcome，或者一个明确的无变更终态。

### 8.1 典型场景

**设计讨论**

```text
outcome=canonical_change(METHOD/DECISIONS)
```

三席贡献 → synthesis → 用户接受 → 生成 docs author assignment → 正常 gate/merge →
receipt 后关闭 discussion。

**实现方案咨询**

```text
outcome=assignment
```

讨论不等代码完成；它以用户认可并发布实施 assignment 为终点。代码交付是下游
assignment 的生命周期。

**纯问答咨询**

```text
outcome=answer
```

synthesis 被 resolver 接受并归档后即可关闭，不发明无意义代码 PR。

**事故复盘**

```text
outcome=canonical_change + followup assignments
```

如果只是三篇“我们学到了什么”而没有 resolution/变更/backlog owner，复盘尚未
完成，只是收齐了输入。

**无共识**

```text
state=ESCALATED
```

由用户选择新一轮、改 outcome、defer 或 cancel；hctl 不自行平均三席意见。

## 9. Gate report memo 的时序修复

Discussion contribution 与 gate report 不是同一种义务，但应复用同一个 memo
artifact 层。

当前“report 必须先在 base 可达”与“verdict memo 先开不合”互相打架。提案：

1. `hctl memo submit <gate-obligation>` 先创建 durable report artifact；
2. `hctl verdict` 引用该 artifact 的 submission OID，而不是要求它已在 main；
3. derive 验证 artifact ref、commit、path、blob 与 gate holder；
4. report 未 archive 时 verdict 可显示为 `REPORT_PENDING_ARCHIVE`，不能静默丢失；
5. 一轮 required reports 全部 submitted 后，hctl 一次 batch archive；
6. archive receipt 验 blob identity 后，verdict 才进入最终 countable 状态；
7. candidate freshness 仍按 exact revision / conservative carry，不因报告存储偷换
   被审代码。

Claude 可重点挑战第 4–6 步是否应让 verdict 在 archive 前完全不计票，或允许
“provisionally countable but merge-blocked”；无论选哪种，都必须由状态机表达，
不能再靠“先看 memo 再手工批合”。

## 10. 最小事实扩展

这不是给现有命令套 shell。至少需要把以下控制事实升入 schema：

```text
DISCUSSION_OPEN
MEMO_SUBMITTED
DISCUSSION_FREEZE
SYNTHESIS_SUBMITTED
DISCUSSION_RESOLVE
```

可以讨论是否将它们折叠为动态 `ASSIGN + COMPLETE` 通用事件；但禁止用 NOTE
承载，因为 NOTE 若能改变下一步就已经是控制事实。

最小不变量：

1. `DISCUSSION_OPEN` 必须是 user-authorized。
2. participant 只能在自己的 seat chain 提交自己的 contribution。
3. 每席每 revision latest submission wins，但 freeze 钉 exact event OID。
4. independent mode 在本席提交前不由 hctl 暴露 peer content。
5. freeze 只能由 coordinator CAS，且 participant quorum 已满足。
6. synthesis 必须引用 frozen packet，不能混入未冻结 amendment。
7. resolution 只能引用本 discussion 的 synthesis。
8. `accepted` 必须满足 outcome contract；否则不能 CLOSED。
9. no-change/deferred/canceled 必须有 user resolution 和原因。
10. 所有 artifact object 不可读、ref 回卷、blob 不匹配均 fail-closed。

## 11. Activation 影响与最小拉回范围

按“hctl CLI 贯穿整个过程”的产品要求，memo plumbing 与 consult kind 不再是普通
P2 便利功能，而是 activation 前缺失的控制面。

不必把动态 HANDOFF、presence、daemon、自动 merge train 等整个 P2 一起拉回。
建议增加一个 bounded vertical slice：

```text
p1-discussion-kernel
  A. outcome contract + discussion facts
  B. memo artifact begin/submit
  C. independent barrier + freeze
  D. synthesis + resolution
  E. batch archive
  F. outcome → existing assignment/PR DAG bridge
  G. hctl-only GitHub path
```

同时需要 supersede：

- D-10 的“memo 即合”改为“submission 不进 main；按 obligation policy 归档”；
- D-11 从 prose consultation 提升为可执行 control flow；
- D-30 扩充事件闭集；
- D-40 report source 与 code base reachability 解耦；
- D-41 用 artifact/archive 状态替代“开而不合”的人工纪律；
- D-43/D-44 消除“列出 memo helper、又把 plumbing 推 P2”的阶段矛盾。

## 12. Acceptance corpus

至少应固化：

1. **Standalone answer**：一席 answer synthesis 被用户接受，归档后 CLOSED。
2. **Independent all-of**：三席未齐时 freeze/peer show/archive 全拒；齐后 exact
   freeze 成功。
3. **Amend race**：freeze 与 amendment CAS 只能有一个确切 packet，禁止半新半旧。
4. **Wrong seat**：一席不能替另一席提交 memo。
5. **Opaque content**：正文任意合法 UTF-8 不影响控制判定；metadata 缺失则拒。
6. **Gate report**：未归档、已归档、blob 被换、artifact ref 回卷四态清楚。
7. **Outcome not landed**：synthesis 已接受但 canonical PR 未合，discussion 不得
   CLOSED。
8. **No-change**：无 PR，但 user resolution 完整时合法 CLOSED。
9. **Direct gh bypass**：无 receipt 的 archive/outcome merge 显像并阻断写动作。
10. **Current incident vector**：同一 #77/#78/#79 型事实快照下，三席
    `status --json` 必须得到相同 state/blocked_by/next_action。
11. **Stub negative**：把 GitHub adapter 换成 no-op，open/archive/land 不得假绿。
12. **Mutation sensitivity**：拆掉 participant barrier、freeze OID 或 outcome
    closure 任一 guard，对应 corpus 必红。

## 13. 希望后续讨论重点攻击的问题

1. `resolution package` 是否足以统一 code/doc、assignment、answer 与 no-change，
   还是应拆成更窄的终态 union。
2. contribution artifact 应使用独立 durable ref，还是继续一个 memo 一个 PR；
   本案倾向 durable ref + 一轮一次 archive。
3. independent veil 的机械边界是否符合“防失误、不防恶意”的信任模型。
4. freeze 应为显式 event，还是可从 all-of submissions 唯一推导；本案倾向显式
   CAS freeze，避免 amendment race。
5. gate verdict 在 report archive 前应是 `pending` 还是可 provisional count；
   merge 必须始终要求 archive verified。
6. discussion 的 `outcome=assignment` 是在 assignment 发布时关闭，还是一路追踪到
   下游代码 merge；本案倾向由 outcome contract 明确 closure horizon。
7. 一轮 archive PR 与 canonical outcome PR 分开是否是正确默认。
8. activation 前最小竖切是否还能再缩，但不能重新退回 prose 选择。

## 14. 本案建议

对“discussion 最后落在哪里”的最终建议是：

> 每个 discussion 在打开时先说清楚自己要生产什么；最后落在一个机器可验证的
> resolution package 上。个人 memo 永远只是证据，不是完成信号。

对 kernel 边界的最终建议是：

> Git 与 GitHub 继续作为 hctl 的底层驱动存在，但从 user/LLM 的正常命令面消失。
> 席位只做领域动作；什么时候 push、开 PR、等待、批合、验证和关闭，由 hctl
> 根据 facts 唯一推导。

这才把今天的三种散文解释，变成一个所有席位都会得到相同答案的 kernel 状态机。
