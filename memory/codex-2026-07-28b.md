# Codex Memory 2026-07-28b — Activation 前回顾：九类问题与待接受边界

> 性质：activation 前讨论轮的 Codex 独立归因与讲人话摘要，**不是 gate
> verdict**，不改变任何 assignment、finding 或 quorum 状态。
> 会话实况：Codex / GPT-5.6 Sol / max effort。

## 0. 总判断

这么久的开发，暴露的不是几十个互不相关的小 bug，而是一个共同问题：

> 很多本该由结构和机器保证的事情，最初依赖了文字约定、人的记忆和
> “看起来已经绿了”。

反复出现的是五种错觉：

1. 文字写了，等于系统知道；
2. 命令成功，等于语义正确；
3. 测试绿了，等于真的测到了目标；
4. 还叫同一个 PR，等于还是同一个被审版本；
5. 操作者一贯可靠，等于流程不需要机械护栏。

下面九类问题，基本都是这五种错觉在不同层面的表现。

## 1. 流程允许一次普通手误变成严重事故

最典型的是 PR #25：没有任何 required verdict 就被合并。随后处理事故时，又因为
手写 PR 编号、把多条命令串在一起，误关了另一个 PR。

这不能只归因于“操作不仔细”。真正的问题是：

- 未过 gate 的 PR 居然能够被 merge；
- PR 编号靠人猜，没有从当前 branch/obligation 解析；
- 多个有副作用的动作之间没有检查点。

一个正常的人为失误，因此被系统放大成了 merged-ungated 审计债和整条
fix-forward 链。事故三因及影响见
[claude-2026-07-27l](claude-2026-07-27l.md)。

## 2. 绿灯可能是假的

P1 corpus 曾出现过最危险的一类 false green：

- runner 没证明 #1..#28 全部真实存在；
- 缺案例、SKIP 也可能成功；
- 把 `HCTL` 换成 `/usr/bin/true`，仍可能 30/30 全绿；
- 有些负例确实失败了，却败在更早的无关检查；
- Python oracle 与真正的 Go kernel 对同一 known event 判断不同；
- 测试只 grep 宽泛错误码，没有证明题面那道 invariant 真被触发。

人话就是：**试卷显示满分，但有些题没答，有些题答错位置也算对。**

后来验收标准才逐步补齐为：

- 原始 reproducer 原样固化；
- 至少一个相邻 mutation；
- happy path 与 fail-closed path 成对；
- 同 payload 的 kernel/oracle 差分；
- 临时拆掉关键 guard 时，本案必须转红。

这也形成了一条明确严重度规则：如果交付物本身就是 required acceptance corpus，
那么“实现错了而 corpus 仍会绿”本身就是 P1，不能因为别处另有 unit test 而降级。
完整谱系见 [codex-2026-07-27g](codex-2026-07-27g.md) 和
[codex-2026-07-27j](codex-2026-07-27j.md)。

## 3. Author 和两席 gater 心里的“修好了”不是同一个函数

这是多轮横向拉锯的最大来源：

- author 修了 finding 中点名的例子；
- spec gater 认为主路径和规范权威已经基本符合；
- precision gater 认为背后的整条 invariant 仍有洞；
- finding 在转述中，又从“规则”退化成了“例子”。

于是会出现一方说 `ADDRESSED`、另一方说不能 `CLOSED`，甚至“✅，但仍有 gap”
这种互相冲突的信号。

这不是谁更严格，而是当时没有统一：

- 唯一 frozen head；
- 唯一 closure ledger；
- 每条 finding 的原始 invariant 和 closure contract；
- 谁拥有 `CLOSED` 权；
- 一轮 repair 的 push budget 和终止条件。

后来的 frozen packet、reconciliation barrier、唯一 ledger、author 一次 push、
owner `fix_verification + delta`、未闭合即 `ESCALATED`，都是在补这个缺口。
完整复盘见 [codex-2026-07-27j](codex-2026-07-27j.md)，现行规则见
[METHOD §8](../METHOD.md)。

## 4. Prose 里写了依赖，不等于结构里真的有依赖

早期 assignment 会出现：

- prose 说 corpus 依赖 kernel；
- 结构化字段却写着 `needs=[]`；
- 可先起草的 corpus skeleton 与必须接真实 CLI 的验收混在一个任务；
- PR 甚至修改了定义自己义务的 frozen assignment。

这样一来，义务边界会在评审途中变化：到底该交什么、依据哪个 revision、旧
verdict 是否仍有效，都可能漂移。

教训是：

> 会影响义务、权限和验收的内容，必须进入规范化结构和 hash；不能只写在说明里。

同理，assignment、obligation、revision 都必须有规范字节和稳定 ID；字符串拼接、
键顺序、Unicode 表示或“大家知道指的是哪个”都不能成为安全边界。

## 5. Git 不是一个大号原子数据库

设计过程中陆续发现：

- push 不是完整 mutex；远端成功的那一刻才是线性化点；
- crash 或网络未知结果需要 pending journal 和 ancestry recovery；
- 两条不同 seat ref 不能共同裁决一次跨席 HANDOFF；
- 每个 PR 各拿一个 merge claim，不能阻止两个 PR 同时 merge；
- tree 相同不代表历史相同；
- branch 被删、PR 标题写 merged，都不能证明发生过合规合并。

因此才需要：

- claim OID 作为 fencing token；
- repo-wide、容量为 1 的 merge coordinator；
- receipt 记录结构化合并事实；
- ancestry、parent、base、tree 和 exact head 联合验证；
- 未知结果恢复，而不是凭印象重试。

跨 seat HANDOFF 则明确延期：在没有单一仲裁域以前，不假装 P1 已经安全解决。

## 6. 遇到“不知道”，实现曾倾向于当成“没有”

这在安全内核里尤其危险。真实出现过：

- 历史 TOML 读失败或类型错误，被压成 `false`；
- 未识别或不完整的事实，接近被当成空事实；
- doctor 只 warning，但实际 producer 会拒绝同一 payload；
- cutover acknowledgment 一度把未获授权的 debt 类别一起降级。

正确原则后来统一成：

> corrupt、unsupported、unknown 都不是 empty；无法证明安全，就不允许写。

这条原则贯穿 kernel、doctor、receipt、cutover 和 acceptance corpus。所谓
fail-closed 也不能只靠方向直觉，必须由真实对象反例和 mutation test 证明。

## 7. 身份、归因和本地状态比预想中更容易串线

真实出现过：

- commit trailer 用错 bot 邮箱；
- 模型 effort 缺失；
- Grok commit 带了 Claude 的归属；
- linked worktree 共用 CommonDir 配置，不同 seat 覆盖彼此的 `local.toml`；
- doctor 与生产命令对同一身份冲突给出相反裁决；
- 本应离线的本地操作，因为顺手观察 remote 而失败。

这说明 seat、模型、邮箱、worktree 和 session evidence 是不同概念，不能靠
“差不多能推出来”混用。

当前方向是 per-worktree 隔离、统一解析链、producer/doctor 共享硬冲突判定、
本地路径显式离线、模型与 effort 缺证据即失败。不同 harness 的 session evidence
自动适配仍属于 P2。

## 8. Exact revision 是正确安全核，但会制造自激振荡

Gate 必须绑定 exact `{base, head}`，否则评审对象可能偷偷变化。但每份 gate memo
一合 main，base 又会前进，于是旧 verdict 失效，形成：

```text
rebase → re-nail → 新 memo → base 再变 → 再 rebase
```

我们还试过用 `git patch-id --stable` 判断“代码其实没变”，后来发现它会忽略
部分空白差异，对 Python、YAML、Makefile 都不能作为安全边界。单看 full tree
也不对，因为 memo-only base 前进后，重放 candidate 的整棵树本来就会变化。

最终方案分两层：

- 流程层：两席审同一 frozen head，memo 批合，只做一次 final rebase/re-nail；
- 内核层：用保留 author、完整 message/trailer、精确 tree delta、mode、binary
  和 whitespace 的 candidate fingerprint 做等价 carry。

不能证明等价就失效，不猜。因此，过去的往返有一部分是语义分歧，另一部分是
freshness 机制自己制造的 Git 往返。

## 9. Activation 不是改一个配置值

如果直接把 `enforcement=bootstrap` 改成 `active`：

- bootstrap 期间已有的 `UNRECORDED_MERGE` 会让 WriteGuard 永久拒写；
- activation 自己又无法事先依赖“已经 active 的 hctl”批准自己；
- 简单切回 bootstrap 会破坏单调性，不能作为普通 rollback。

所以需要有边界的 cutover：

- cutover 之前已有的特定 `UNRECORDED_MERGE` 只降为历史 warning；
- 不把这些债伪装成已修复，也不让它们产生新 authority；
- cutover 之后的新 merge debt 继续硬拒绝；
- `INVALID_RECEIPT`、`UNJUDGEABLE_MERGE` 不能借 cutover 一起放过；
- integration 必须受 ancestry 约束，不能仅凭 tree equality 猜历史。

这意味着正式 activation 是一次**语义上的单向切换**。异常处置以 fix-forward
为主，不能把“切回 bootstrap”当作无害开关。cutover 的终验见
[codex-2026-07-28](codex-2026-07-28.md)，终端序列设计见
[codex-2026-07-27k](codex-2026-07-27k.md)。

## 10. 当前状态：哪些已封口，哪些仍是明确边界

### 10.1 已经转成机制的部分

P1 当前已经为下列问题建立了结构化封口：

- exact assignment / obligation / `{base,head}` 身份；
- claim CAS、fencing 与 pending recovery；
- required quorum、单一 merge coordinator 与 receipt；
- strict corpus manifest、真实 wire stamp、唯一 Go known-type authority；
- finding owner、reconciliation barrier、单 repair push；
- conservative candidate carry；
- attribution 的 per-worktree 隔离与 fail-closed；
- 有界 bootstrap cutover 和 post-cutover 硬拒绝。

这里的“已封口”是指设计和实现已有机械约束；正式 activation 后仍须用生产配置
和精确 kernel build 做一次端到端确认。

### 10.2 有意留给 P2/P3 的部分

下面不是忘了做，而是 P1 没有承诺：

- bootstrap 历史债只被承认和隔离，没有补造 receipt；
- review ledger 目前仍部分依赖流程纪律，结构化 ledger 工具留在 P2；
- merge 执行仍需人工触发，没有 daemon、timer 或 webhook；
- dynamic assignment、跨席 HANDOFF、repair command 尚未交付；
- `authority:user` 是单一可信用户模型下的声明，不是密码学身份证明；
- 多用户互不信任不在当前安全模型；
- 各 harness 的模型/effort session evidence adapter 未完整实现；
- hctl 是 collaboration kernel，不负责窗口、进程和整个工作流编排。

这些边界可以接受，但必须被明确接受；不能在 activation 后把它们误认为已经具备。

## 11. Activation 前真正需要讨论并裁定的五件事

1. 是否接受 bootstrap 历史债以“有界 warning”存在，而不是 activation 前全部修复。
2. 是否接受 P1 仍有少量人工步骤和级④流程约束。
3. 是否接受当前单用户信任模型，而不把它描述成多人对抗安全系统。
4. 是否接受 activation 基本是单向 cutover，异常时采用 fix-forward。
5. 是否已经准备好固定精确 kernel build、配置变更，并执行 activation 前后的
   doctor/status、历史 warning 边界和 post-cutover 负例复验。

如果这五项都接受，就没有必要在 activation 前重开已经关闭的算法问题；应进入
一次有清单、有精确 revision、有事后验证的 cutover。

如果其中任何一项不接受，也不应把问题模糊地描述成“代码还不够稳”，而应明确指出
需要把哪一项 P2 能力提前到 activation 之前。

## 12. 一句话收束

这段开发最大的收获，不是修了多少 bug，而是逐步识别出哪些事情绝不能再靠
“大家应该都明白”：

> 绿必须能证明为什么绿；义务必须有稳定身份；历史必须有可验证事实；分歧必须
> 统一收敛；不知道必须失败关闭。

现在大部分核心风险已经被转成可计算的身份、revision、事件、receipt 和
fail-closed 规则。activation 前剩下的核心问题，不再是“还有没有零 bug”，而是
我们是否清楚并愿意接受 P1 刻意留下的人工与信任边界。
